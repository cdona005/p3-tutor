A model alone cannot act 3 min

You send "fix the failing test" to the model API. It replies with a tool_use block asking to run pytest. Nothing runs it, and nothing carries it into your next call: the Messages API is stateless, so your code must resend the whole history every time (Using the Messages API). What now?

# One bare call to the model API
reply = client.messages.create(
    model=MODEL, max_tokens=1024, tools=TOOL_SCHEMAS,
    messages=[{"role": "user", "content": "Fix the failing test"}],
)
print(reply.stop_reason)   # "tool_use"
print(reply.content[-1])   # tool_use block: name="Bash", input={"command": "pytest"}
# Nobody runs pytest: the reply is only a request.
# Nobody stores this exchange: the next create() starts blank
# unless your code resends the history.

The model only returns a structured request. For tools you define, it answers stop_reason: "tool_use", and your code runs the operation and sends back a tool_result (Tool use with Claude).

The code you write to fill that gap is the agent harness. Anthropic's definition, written for Claude Code, names two of the duties:

  • Claude Code "is the layer around the model that provides the tools and manages the context the model sees. This surrounding layer is what the term agentic harness refers to" (How Claude Code works).

This lesson's own grouping adds the rest, for four duties, one per section after this: loop and tools (running the loop and executing tool calls), context, limits, and permissions.

The loop and tool execution 2 min

Lesson 1 said the loop exits when a reply has no tool call. But the model does not call itself. So who is "the loop"?

The harness is. In CS terms the model is one function, call_model, and the harness is the main that calls it again and again. Here is a minimal version, with each line marked by the duty it serves:

messages = [user(prompt)]
while True:                                      # LOOP
    reply = call_model(messages, TOOL_SCHEMAS)   # LOOP: one turn starts here
    messages.append(assistant(reply.content))    # LOOP: keep the history
    calls = [b for b in reply.content if b.type == "tool_use"]
    if not calls:                                # LOOP: the model's exit (caps add more, section 4)
        break
    results = []
    for call in calls:                           # TOOLS: the harness acts
        output = TOOL_IMPLS[call.name](**call.input)  # TOOLS: your code runs it
        results.append(tool_result(call.id, output))
    messages.append(user(results))               # LOOP: feed results back
  • A turn is one pass: the model produces output, the harness runs any tools it requested, and the results go back to the model, with no control returned to your code in between (Agent SDK: how the agent loop works).

The real harness adds the other duties around this skeleton, as the next sections show.

Context management 2 min

The tutor has run 40 turns reading big files and the window is nearly full. What happens on turn 41, and what happens to the rule you gave in your first message?

The model only sees what the harness puts in front of it. That window does not reset between turns. Everything accumulates: the system prompt, tool definitions, conversation history, and the inputs and outputs of every tool call. Reading one big file can cost thousands of tokens in a single turn (Agent SDK: how the agent loop works).

Near the limit the harness does compaction: it summarizes older history to free space and emits a compact_boundary message. A summary is lossy, so specific instructions from early in the conversation may not survive (same page).

  • Where to put rules that must last: in CLAUDE.md, the project instructions file the harness loads into every session. Its content is re-injected on every request, so compaction does not summarize it away. A rule typed in the first message is just history.
  • Remembered is not enforced: CLAUDE.md keeps a rule in view, but the model can still ignore it. To make a rule hold, block the tool call itself with a permission rule or a hook, your own code that runs before a tool (section 5).
  • How to keep the window small: use a subagent, a separate agent the main one starts for a subtask, with its own fresh context. It returns only its final response, so the main context grows by a summary, not by its whole transcript.

Limits 2 min

An agent loops on a failing test overnight, calling tools every turn. What stops it? Without limits the loop runs until the model finishes on its own, and both max_turns and max_budget_usd default to no limit (Agent SDK: how the agent loop works). If the model never stops calling tools, the SDK does not stop it either.

That is why limits are a harness duty. The model sees only the messages the harness sends it; the turn count and the spend live in the harness, so only the harness can enforce a turn or spend cap across calls. (The API's max_tokens caps a single reply, nothing more.) Anthropic notes it is common to include stopping conditions such as a maximum number of iterations to keep control (Building effective agents).

CapCountsDefaultSubtype on hit
max_turnsTool-calling turns, plus one for the final replyNo limiterror_max_turns
max_budget_usdEstimated spend, subagents includedNo limiterror_max_budget_usd
  • A capped run has no result, so check the subtype first (lesson 1).
  • The budget is checked after each response arrives, so spend can pass the cap by up to one response, plus subagents still running.
  • Trade-off: a cap that is too low cuts off a good run; none at all costs real usage on your subscription. To choose: read num_turns from a normal run, set max_turns a little above it (the final reply counts too), and leave the budget room for one extra response.

Permissions 2 min

The model requests rm -rf build/ through Bash. Who decides whether it runs, and what does the model see if the answer is no?

The harness decides, before the tool runs. You steer it with these settings (Agent SDK: how the agent loop works):

  • allowed_tools auto-approves the tools you list.
  • disallowed_tools blocks the listed tools, whatever else is set.
  • permission_mode sets how much approval is needed, from asking about each call to skipping approval.
  • Hooks are your own code the harness runs at fixed points; a PreToolUse hook runs just before a tool and can block the call. They run in your application process, so they use no context.

Why the model cannot be its own gate: asking it to refuse is advice it may not follow, while a harness that never executes the call is a rule. The gate has to sit in the code that runs the tool.

The key behavior: when a tool is denied, Claude receives a rejection message as the tool result and typically tries another approach or reports that it could not proceed. The run goes on.

This reaches your tutor. In a bench run, a tool that would need a prompt is denied, because no one is there to answer. Only the tools in permissions.allow plus Glob and Grep are pre-approved, so a skill that needs Write will have its write rejected and may never produce its file.

A common mix-up

"A denied call ends the run." Programs usually signal refusal with an exception. Here the model reads the rejection and carries on, so the failure shows up later as a missing file, not a crash.

Worked example and practice 2 min

Worked example

A bench trace: "Teach run. Subtype error_max_turns, num_turns 25; the config sets max_turns to 25. No lesson file. One tool call per turn: 21 Read, 4 Grep, no Write." Which duty explains it?

  1. Read the subtype first: error_max_turns. A limit fired, so the run did not finish and has no result.
  2. Name the duty: limits. The cap came from the config (the default is none), and num_turns equals max_turns, so it was reached.
  3. Ask why it was reached. Every turn called a tool and none wrote the file, so the cap hit before the final reply. The loop ran as designed; the skill spent its turns on reads.
  4. Choose a fix: change the skill so it reads less, or raise max_turns on purpose above a normal run's num_turns.

Show a solution
  1. Permissions, because Write was denied. (Context was given: compaction can summarize a first-message rule away.)
  2. A rejection message as the tool result, not a crash. It tried another approach, which was printing the lesson in chat.
  3. Move the rule into CLAUDE.md, which is re-injected every request, so it stays in view, and add Write to permissions.allow if the skill should write files.

Summary 1 min

Why a harness: the model returns text or a tool request, and nothing else. It does not run its tools, keep its own history or enforce its own caps.
