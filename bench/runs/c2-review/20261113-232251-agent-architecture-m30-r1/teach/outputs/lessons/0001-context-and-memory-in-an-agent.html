Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in a saved note, or in a searchable manual, and say why.

Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three are context and memory decisions, and you will defend them at your design review.

Warm-up 2 min

Two questions from earlier sessions. Answer in your head first.

Recall

1. In the agent loop, who actually runs a tool: the model or the program around it?

2. Why can a chatbot state an outdated fact with confidence?

Check your answers

1. The program. The model only writes a request that names the tool and its arguments; the program runs it and sends the result back, and then calls the model again.

2. Its knowledge stops where its training data stops, and it writes plausible text either way.

Both matter today. The "result goes back to the model" step is how the context grows, and the "knowledge stops at training" fact is why the assistant needs your manuals and bookings supplied as text.

The context window: everything the model can see 5 min

A student asks the assistant, "How long do I let the laser cutter warm up?" The model was never trained on your makerspace's manual. So where does the answer come from? From the text your program puts in front of the model on that call, and nowhere else.

The set of tokens the model is given when it writes a response is its context (Anthropic, context engineering). The limit on how much fits is the context window. The official docs define it as "all the text a language model can reference when generating a response, including the response itself", and call it a kind of "working memory", different from the training data (Claude docs, context windows).

If you know Python, think of the context as the arguments to one function call. What the model writes depends only on what is passed in: whatever is not passed in does not exist for it. The analogy breaks in one place: the arguments here are a flat run of text, and the model reads all of it every time.

What is in it

The docs list what counts toward the window: "the system prompt, every message in messages (including tool results, images, and documents), and your tool definitions", plus the output the model generates (Claude docs). For your assistant that is:

  • the system prompt: its role and rules;
  • the tool definitions: names, descriptions and parameters;
  • the conversation so far: student messages, the model's tool requests, the tool results;
  • the model's own reply as it is written.

You have heard the word token: a chunk of text, usually a word or a piece of one, which is the unit the model reads and writes. The window is measured in tokens, and so is your bill, because usage is metered by the tokens sent in and the tokens written out. Anthropic's retrieval article equates 200,000 tokens with about 500 pages of material (Anthropic, contextual retrieval).

Bigger is not free

Windows are large now; the docs say up to 1M tokens depending on the model, with some models at 200k. So why not stuff in every manual and stop thinking? Two reasons.

  • Accuracy. "As token count grows, accuracy and recall degrade, a phenomenon known as context rot" (Claude docs). Anthropic calls context "a finite resource with diminishing marginal returns" and describes an "attention budget" that every new token uses up a little (Anthropic). It is a gradient, not a cliff.
  • Cost. You pay for the tokens you send. The goal, in Anthropic's words, is "the smallest possible set of high-signal tokens" that gets the outcome you want.
Prompt caching lowers the price of tokens you resend, but the docs are explicit that cached prefixes "still occupy the context window": it changes what you pay, not whether they count.
A common mix-up

"The model has read the manuals, so it knows them." Training is not the context. Anything the model needs about your makerspace must be in the context on the call, or it must be fetched into it by a tool. A model that is not given the laser cutter manual will still answer, fluently, and may invent the warm-up time.

Between steps: the context grows 6 min

In the agent loop, each step is a separate model call. The model does not keep a running thought between calls. So how does step 3 know what step 2 found? Because your program sends the earlier steps again, inside the new call. The docs describe each turn's input as "all previous conversation history plus the current user message", and the output of one turn "becomes part of the input for the next turn" (Claude docs).

This is a list you append to. In Python terms:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # sees ALL of messages
    messages.append(reply)                                # its request joins the list
    if reply is a final answer: break
    result = run_tool(reply)                              # the program runs it
    messages.append(result)                               # the result joins the list

The list is the working memory of the run: it is what the agent "remembers" between steps, and it is nothing more than the list you chose to resend. That puts you in control, and it puts the cost in your hands too: every call pays for the whole list again.

In a run like this, tool results tend to be the biggest part: in the worked example in Section 5, they are 4,500 of the 6,700 tokens in call 4. A manual search that returns three whole pages adds thousands of tokens, and those tokens ride along on every later call. Anthropic's guidance for tools is that they should return information that is "token efficient" (Anthropic). For your assistant, that means check_calendar should return the open slots for one machine and one day, not the whole month's booking table.

When the list gets too long

A long run can fill the window. If the input alone is too large, the API returns a "prompt is too long" error (Claude docs). Long before that, context rot hurts quality. Anthropic's techniques for long tasks are compaction, note-taking and sub-agents, and clearing old tool results is the lightest form of compaction (Anthropic; Claude docs). Two of them apply here, and the third comes in the next section:

  • Tool result clearing: drop old tool results that are no longer needed. The lightest option.
  • Compaction: summarize the conversation as it nears the limit and continue with the summary in place of the old messages. Tune it to keep what matters (decisions, open problems) and drop the rest. The catch: the summary is itself written by a model call, which costs tokens, and a detail it leaves out is gone.
  • Sub-agents: give a focused task to another agent with a clean context, which may use tens of thousands of tokens but hands back a short summary, often 1,000 to 2,000 tokens. You will meet this again when we discuss splitting work across agents.

Rule of thumb for your assistant: a booking chat needs a few tool calls, so keep results small first; add clearing if runs get long; reach for compaction or sub-agents only if a single task really fills the window.

A common mix-up

"The model remembers step 2 because it just did it." It does not. Each call starts blank except for what your program sends. If you drop a tool result from the list, the model has no trace that it ever saw it.

Check yourself

Midway through a run, one tool result is a 5,000-token manual page. The model has already used it, and its conclusion is stated in a message that stays in the list. Which change keeps later calls cheaper without breaking the run?

Show the answer

Clearing the used result. Clearing is safe only when the result's content is no longer needed, or its conclusion lives elsewhere in the list; otherwise the model loses it for good. Telling the model to ignore the page leaves the tokens in the input. A bigger window only raises the limit.

Between sessions: nothing is kept unless you keep it 5 min

On Monday a student completes laser cutter training. On Thursday they ask to book the laser cutter. Does the assistant know they are trained? Only if something carried that fact from Monday to Thursday. The context from Monday is gone: the message list lived in your program's memory for one conversation, and Thursday starts a new list.

So memory between sessions is whatever your program saves outside the context and loads back in. The model has no memory of its own. Memory of past conversations is not automatic, however natural it feels in a chatbot app.

Notes as memory

The simplest design is structured note-taking: the agent writes notes that persist outside the context window and reads them back later (Anthropic). Anthropic's examples include a to-do list or a NOTES.md file. If you are comfortable with Python, the shape is familiar: a JSON file or a database table keyed by student.

{
  "student_id": "s-10482",
  "trained_on": ["laser_cutter", "3d_printer"],
  "booking_notes": "prefers evening slots",
  "updated": "2026-11-09"
}

The flow, each visit:

  1. The program loads this student's record and puts it in the context, a few dozen tokens.
  2. The conversation runs, and the model can use the record.
  3. When something worth keeping changes, a tool such as save_note or update_training writes it back to the file.

Your program, not the model, decides what to load: here, one record, looked up by the student's ID when the chat opens. Loading too much costs tokens on every call, and a stale record misleads the model, which will trust what it is given. Put the date in the record, as above, so old entries can be checked.

What to save, and what not

  • Save: facts that stay true and that a later session needs: training status, a stated preference, an open booking issue.
  • Do not save: the whole transcript. It is large, mostly irrelevant next time, and would eat the window on every future visit. Save a short note, and the model can write it or your program can.
  • Be careful with: facts that change or can be wrong. A saved "trained on laser cutter" must come from the training system or a staff action, not from a student saying it. Decide who is allowed to write each field.
Notes help inside one long task too: an agent that writes progress to a file can recover after a compaction or a restart. Anthropic gives this as a way to keep track of milestones in long tasks.
A common mix-up

"A bigger context window means the assistant remembers students." A window is per conversation. However large it is, it is empty when a new session starts, and storing everything would just make each new session slow and expensive. Memory across sessions is storage plus a rule for what to load.

Check yourself

A student tells the assistant, "I finished the 3D printer course yesterday." What should the assistant do to remember this next week?

Show the answer

The third option. Memory is saved outside the context, and it should be short and trustworthy. The transcript option wastes tokens, and doing nothing loses the fact.

Retrieval: finding the right page 6 min

Your manuals total hundreds of pages. A student asks about the error code on the vinyl cutter. You cannot send every manual on every call: it costs too much and invites context rot. How does the assistant get the one relevant page in front of the model?

Retrieval means searching a store of documents and putting only the best matches into the context. A tool such as search_manuals(query) does it: the model writes the query, the program searches, and the top passages come back as the tool result.

First, check whether you need it

Anthropic says that if your knowledge base is smaller than 200,000 tokens (about 500 pages), you can just include the entire knowledge base in the prompt, with no retrieval, and that prompt caching makes this faster and cheaper (Anthropic, contextual retrieval). The article is from 2024, so check the numbers against your model. Measure your manuals: if they fit, this is the simplest design, and "do the simplest thing that works" is Anthropic's own advice (Anthropic). Even then, context rot and cost still argue for sending less.

How retrieval works

  1. Chunk the manuals into passages, for example a few paragraphs each.
  2. Index the chunks so they can be searched.
  3. Search at question time and return the top few chunks.

An embedding is a list of numbers a model produces for a piece of text, built so that texts with similar meaning get similar numbers; search then means finding the chunks whose numbers are closest to the question's. Two kinds of index are common, and they fail in different ways (Anthropic):

Search typeFindsMisses
Embeddings (meaning)Chunks that mean the same thing, in different words: "machine gets hot" matches "overheating"Exact identifiers, such as an error code like "E-47"
BM25 (keywords)Chunks containing the exact words or codes in the queryParaphrases with no shared words

BM25 is a keyword-ranking method: it scores each chunk by how well the query's words, especially rare ones, appear in it. Anthropic's own example is the query "TS-999": embeddings may miss the exact identifier, and BM25 finds it. The usual answer is both: run the two searches, merge the results, drop duplicates, and send the top few chunks on. For a manual full of model numbers and error codes, a hybrid is the safer default.

A common mix-up

"Retrieval means the right page is always found." It does not. Anthropic's reported failure rate, defined as the share of queries where the right chunk was not in the top 20, was 5.7% for plain embeddings on its test set (Anthropic). Those are 2024 numbers on other data, so treat them as a sense of scale. If the right chunk is not retrieved, the model answers without it, and may do so confidently. Test retrieval on real student questions.

A chunk must make sense alone

A chunk loses the page around it. Anthropic's example is "The company's revenue grew by 3% over the previous quarter": no company, no period. In your manuals, a chunk reading "Set the speed to 40% and the power to 60%" does not say which machine or which material. Retrieval will find it for the wrong machine. The fix Anthropic reports is to add a short, chunk-specific note, 50 to 100 tokens, saying where the chunk comes from, before indexing it. It calls this "contextual retrieval". Its top-20 failure rates:

  • plain embeddings: 5.7%;
  • with chunk notes added: 3.7%;
  • with chunk notes and keyword search together: 2.9%;
  • plus reranking, where a second model re-orders the top 150 results and keeps the best 20: 1.9%.

You can get much of this cheaply by storing the machine name, section title and page number with each chunk, and showing them in the tool result. The model then sees "Laser cutter, Cutting acrylic, p. 14" above the passage, and a student can be told the page.

Two ways to load: up front or on demand

  • Up front: the program searches before the model runs and inserts the matches.
  • Just in time: the model holds only lightweight pointers and calls a tool when it needs more. Anthropic notes this is slower than retrieving up front and needs good tools, or the agent can waste context on dead ends, and that a hybrid suits less dynamic content (Anthropic).

Anthropic's just-in-time examples use pointers such as file paths. A search_manuals tool the model chooses to call is the same idea in spirit: the model decides when to fetch, so a booking question never pays for manual text.

Worked example and practice 5 min

What does one request really cost, and which tool design drives it? Here is how Figure 2's numbers came about. The numbers are illustrative; real counts depend on your prompts and tools.

Worked example

The base input (system prompt, tool definitions and question) is 2,050 tokens. The assistant makes three tool calls. Each step adds the model's tool request (50 tokens) and the tool result (1,500 tokens), so 1,550 tokens per step. The fourth call writes the final answer. How many input tokens are billed across the four calls?

  1. Call 1 sees only the base: 2,050.
  2. Call 2 sees the base plus one step: 2,050 + 1,550 = 3,600.
  3. Call 3 sees two steps: 2,050 + 3,100 = 5,150.
  4. Call 4 sees three steps: 2,050 + 4,650 = 6,700.
  5. Add them up: 2,050 + 3,600 + 5,150 + 6,700 = 17,500 input tokens.

The new content over the whole run is only 6,700 tokens, yet 17,500 are sent, because each call resends everything before it.

Your turn

Same run, but search_manuals now returns six whole pages: each step adds 6,050 tokens (50 for the request, 6,000 for the result), and the base is still 2,050. There are three steps and four calls. Compute the input tokens for each call and their total. Step one is given: call 1 sees 2,050.

Show a solution

Call 2: 2,050 + 6,050 = 8,100. Call 3: 2,050 + 12,100 = 14,150. Call 4: 2,050 + 18,150 = 20,200. Total: 2,050 + 8,100 + 14,150 + 20,200 = 44,500 input tokens, about 2.5 times the 17,500 above. If the tool returned just a 500-token passage, each step would add 550, and the total would be 2,050 + 2,600 + 3,150 + 3,700 = 11,500. Small tool results matter more than the window size.

Sort it: the lesson's win

For each item, say whether it goes in the context for this chat only, in a saved note loaded each visit, or in a searchable manual store: (a) the question the student just typed; (b) which machines this student is trained on; (c) the chunk of the vinyl cutter manual on blade depth; (d) the open laser cutter slots for Friday.

Show a solution

(a) Context: it matters only now. (b) Saved note: it stays true across visits and is short; write it only from a trusted source. (c) Searchable manual store: large, rarely needed, fetched when a question calls for it. (d) Context, via a tool call at the time: bookings change, so a saved copy would go stale, and the calendar is the source of truth.

Summary 1 min

  • The context is everything the model can see on one call: system prompt, tool definitions, messages, tool results and its reply. The window limits it, and tokens set the cost.
  • Between steps, the agent "remembers" only the message list your program resends, so every call pays for it again. Keep tool results small; clear or compact when runs get long.
  • Between sessions, nothing persists unless you save it: short, trusted notes, loaded at the start of the visit.
  • Retrieval puts only the best passages in the context. Check first whether everything fits; if not, use keyword plus meaning search, and make chunks self-explanatory.
