Context and memory in an agent

By the end of this lesson you can say, for any piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a searchable manual, and why.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop (your earlier session)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Those are three memory decisions: what to keep in context, what to save, and what to look up. You will make them at your design review, so you need to be able to defend them.

Warm-up 2 min

Recall

From memory: in the agent loop, after the model asks for a tool, who actually runs the tool, and what happens to the result?

Check your answer

The program around the model runs the tool, not the model. It then adds the result to the conversation and calls the model again. That last part is today's subject: "adds the result to the conversation" means the conversation grows with every step, and everything the model knows is whatever is in it.

The context window: all the model sees 6 min

Start with an everyday example. Imagine a help desk where the clerk has total amnesia. Before each question, you hand them a single sheet of paper. They read the sheet, answer, and the sheet is thrown away. If you want them to know something, it has to be on the sheet.

A language model works like that clerk. The context is the text the model is given for one call: the instructions, the tool descriptions, the conversation so far and the tool results. The context window is the maximum amount of text, counted in tokens, that fits in one call. A token is a chunk of text, roughly a short word or part of a word; models read and bill in tokens.

The model keeps nothing from one call to the next. It only has what you send. Anthropic's documentation describes the context window as the model's "working memory" for a request, and notes that it is a different thing from the large body of text the model was trained on (Claude docs: context windows). Window sizes differ by model and change over time, so look up the current number for the model you choose rather than memorizing one.

Two consequences matter for your budget and your design.

  • Cost follows context size. You pay for the tokens you send in and the tokens the model writes. A fatter context costs more on every call, not once.
  • More is not better. Anthropic's engineering team notes that models have a limited "attention budget": as the amount of text grows, the model's ability to recall details from it can decrease, so the goal is the smallest set of high-signal tokens that gets the job done (Effective context engineering for AI agents). The Claude docs make the same point: gains depend on what is in the context, not just how much fits.
A common mix-up

"The model remembers our chat." It feels true because chat apps show you a continuous conversation. But the app is resending the whole conversation each turn. If you forget to send the earlier messages, the model has no idea they happened. Memory is something your program builds; it is not something the model has.

What is kept between steps 6 min

Now connect this to the loop you already know. In an agent, each step is a separate model call. To let the model continue, the program keeps a list of messages and appends to it: the model's tool request, then the tool's result, then the next request, and so on. Every call sends the whole list again. The list is the agent's working memory, and it lasts only as long as the task.

That list only grows. Tool results are often the biggest part, especially a manual search that returns several pages of text.

Because every call resends the list, a long task is billed on the same early text again and again. Some providers let you cache a repeated beginning at a lower price; check your provider's pricing page for how that works. Either way, the habit to build is to keep tool results short.

Ways to keep the working memory small

Anthropic's engineering post lists the main techniques for long tasks (Effective context engineering). In plain terms:

  • Make tools return less. A search tool that returns the three best passages, not twenty pages, saves tokens on every later call.
  • Clear old tool results. Once the model has used a calendar lookup, the raw table of bookings can be dropped from the list, keeping only the conclusion.
  • Compact. When the list nears the window limit, ask the model to write a short summary of the work so far, and start a fresh context from that summary. The cost is that a summary can lose a detail you later need.
  • Hand off to a helper. A second agent does a messy sub-task in its own context and returns only a short result. You will meet this in the multi-agent lesson.
A common mix-up

"A bigger window means I do not need to manage context." It is tempting because a big window sounds like unlimited memory. But a bigger window lets you send more, and you pay for every token on every call, and the model may use long text less reliably. A big window is a ceiling, not a target.

What is kept between sessions 6 min

Working memory ends when the task ends. Next Tuesday, when the same student opens a new chat, the list starts empty. The model does not know who they are, or that they finished the laser cutter safety training last week.

Anything that must survive has to be stored outside the model by your program, then loaded into the context when needed. This is long-term memory for an agent. Lilian Weng's widely cited overview of agents uses this same split: the context window as short-term memory, and an external store the agent can save to and read from as long-term memory (LLM Powered Autonomous Agents).

The simplest long-term memory is a note: a small piece of saved text or data about something worth remembering. For the makerspace, here is a record per student, in a file or database you already know how to use from Python:

{
  "student_id": "s1042",
  "trainings": {"laser_cutter": "2026-10-28", "3d_printer": null},
  "preferences": "usually books evenings"
}

The flow has three moves:

  1. Load. At the start of a session, the program reads the student's record and puts a short summary in the context, for example "Trained on: laser cutter."
  2. Use. The model can now answer "Can I book the laser cutter?" without asking again.
  3. Save. When something changes, such as the student finishing 3D printer training, a tool (for example update_training) writes it to the record.

Two design points to bring to the review. First, decide what is worth saving: training dates yes, the full transcript of every chat probably not, because loading it later fills the context and costs tokens. Second, who writes the note matters. For something that grants access to equipment, such as training status, have your own code or a trusted tool write it, not the model's guess from conversation.

Anthropic's post describes the same idea as "structured note-taking": the agent writes notes to storage outside the context window and reads them back later. It gives a coding agent keeping a to-do file as an example.
A common mix-up

"The assistant will just learn from conversations." A deployed model does not change when people chat with it; its training happened earlier. If the assistant seems to know something from last week, your program saved it and loaded it back. Nothing is saved unless you build it.

Retrieval: finding the right page 6 min

The third problem: the manuals. Suppose the laser cutter manual is 120 pages, about 60,000 tokens, and the makerspace has twenty machines. Putting all the manuals in every call would be slow, expensive and hard for the model to use well. And the whole set might not fit at all.

The fix is retrieval: keep the manuals outside the context, and when a question arrives, find only the few relevant passages and put those in. This is what search_manuals does. Think of a library: you do not carry the building home, you look up the book and bring back the chapter you need.

How it works

  1. Prepare once, ahead of time. Split each manual into chunks, pieces of a few hundred words, such as one section. Store each chunk with a label saying which machine and page it came from.
  2. Search per question. Score every chunk against the student's question and take the top few. Scoring can be keyword matching, or embeddings: numbers computed from the text so that chunks with similar meaning get similar numbers, which lets "the beam is wandering" find a section titled "Mirror alignment". Weng's overview describes this approach: store embeddings in a vector store and use fast similarity search to find the closest ones.
  3. Insert and answer. Return the top chunks as the tool result. They enter the context like any tool result, and the model answers from them, ideally citing the page.

Anthropic's post calls this "just-in-time" context: the agent keeps lightweight references, such as file paths or queries, and loads the data only when needed, rather than loading everything up front. Its trade-off is worth stating at your review: loading on demand is slower and needs good tools, while preloading is fast but wastes context. Many designs mix the two.

A common mix-up

"Retrieval always finds the right page." It finds the best-scoring chunks, which may not be the right ones. A question about "kerf" may not match a chunk that says "cut width". If the retrieved text is wrong, the model may answer confidently from it. Good designs return the page reference so a student can check, and let the assistant say "I could not find that in the manual".

Worked example and practice 3 min

Worked example

A student asks: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The system prompt plus tool descriptions take 1,500 tokens, the question 50. The model makes three tool requests of about 60 tokens each. Results: check_calendar returns 200 tokens, search_manuals 1,500, check_training_record 100. The final answer is 150 tokens. How many input tokens do you pay for across the four model calls?

  1. Call 1 sends the starting context: 1,500 + 50 = 1,550.
  2. Call 2 sends call 1's context, plus the model's request (60) and the calendar result (200): 1,550 + 60 + 200 = 1,810.
  3. Call 3 adds the request (60) and the manual result (1,500): 1,810 + 60 + 1,500 = 3,370.
  4. Call 4 adds the request (60) and the training result (100): 3,370 + 60 + 100 = 3,530. The model then writes its 150-token answer.
  5. Total input: 1,550 + 1,810 + 3,370 + 3,530 = 10,260 tokens, even though the final context is only about 3,700 tokens. The early text is paid for once per call.
Your turn

Same request, but search_manuals now returns 4,000 tokens, not 1,500. Calls 1 and 2 are unchanged (1,550 and 1,810). Work out call 3's input first, then call 4's, then the total. What does that tell you about where to save tokens?

Show a solution

Call 3: 1,810 + 60 + 4,000 = 5,870. Call 4: 5,870 + 60 + 100 = 6,030. Total: 1,550 + 1,810 + 5,870 + 6,030 = 15,260 tokens, about 5,000 more, from a result only 2,500 tokens larger. The big result is re-sent in every later call, so shrinking tool results saves more than trimming anything else, and a tool that returns a long result late in the loop costs fewer repeats than one that returns it early.

Summary 1 min

  • The model sees only the context of the current call; the program rebuilds and resends it every time, and you pay per token.
  • Between steps, the message list is the working memory; it grows, so keep tool results small and clear or compact when needed.
  • Between sessions, nothing persists unless your program saves it (notes) and loads it back.
  • For long documents, retrieval brings in only the relevant chunks, but it can miss, so return page references.
