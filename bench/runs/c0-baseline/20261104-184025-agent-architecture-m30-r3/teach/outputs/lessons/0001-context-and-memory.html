Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context at each step, what gets saved between visits, and how it finds the right page in a long manual.

Objective O3: context and memory in an agent About 30 minutes Builds on: the language model and the agent loop (your earlier sessions)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Every one of those decisions is a decision about context and memory, and you will have to defend them at your design review.

Warm-up 2 min

Recall

Without looking back: in the agent loop, who actually runs a tool such as check_calendar, and what happens to its result?

Check your answer

The program around the model runs the tool. The model only writes a request naming the tool and its arguments. The program then puts the result back in front of the model and calls the model again. That "puts the result back in front of the model" is today's topic: the result lands in the model's context, and the model sees nothing that is not there.

The context window 6 min

Start with a concrete case. A student types: "Is the laser cutter free Friday at 3, and do I need training?" Before the model writes a single word, the program assembles a block of text for it to read. It holds:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Be brief. Never book without confirming.");
  • the tool descriptions for check_calendar, search_manuals and the rest;
  • the messages so far: the student's question, and later the model's tool requests and the tool results.

That block is the context: the set of tokens the model is given when it writes its next output (Anthropic, context engineering). The context window is the limit on how much it can hold: all the text the model can refer to when it responds, including the response it is writing (Claude docs, context windows). Think of it as the model's desk. It can only work with what is on the desk right now.

You met the word token in passing before; here it is properly. A token is the unit of text a model reads and writes: a short word, or a piece of a longer one. As a rough rule, a page of ordinary text is a few hundred tokens. Windows and prices are both counted in tokens, not in pages or words.

Two things make the window matter to you. First, it is a hard limit: if the input is too long, the request fails or the reply is cut short. Second, the window is also what you pay for. Every token the model reads is billed, and every token it writes is billed. Prompt caching can lower the price of repeated tokens, but the docs are explicit that caching "changes what you pay for those tokens, not whether they count" toward the window.

Window sizes vary by model, and recent models list up to 1 million tokens. Check the current docs for the model you pick; the numbers change often, and the design ideas below do not.
A common mix-up

"A bigger window is better, so put everything in." It is tempting because a huge window sounds like it removes the problem. It does not. Anthropic's engineers describe an "attention budget": as the number of tokens grows, the model's ability to recall information from the context decreases, a gradual decline they call context rot. The goal is the smallest set of high-signal tokens that gets the job done (Anthropic). Pasting all your manuals in costs money on every call and can make the answer worse.

Check yourself

Which of these is not counted toward the context window in a request?

Show the answer

The unfetched database rows. Only text that is actually placed in the request counts: system prompt, messages (tool results included), tool descriptions, and the model's output.

What is kept between steps 6 min

Here is the fact that surprises most people: the model keeps nothing between calls. Each step of the agent loop is a separate model call, and the model starts every call blank. The "memory" within one task is just your program keeping a list of messages and sending the whole list again each time. The docs describe it this way: each turn's input is all previous conversation history plus the new message, and the model's output then becomes part of the next turn's input (Claude docs).

Why this drives cost

Because every call resends the history, you pay to read the same early tokens again at every step. A long manual page fetched at step 2 is read again at steps 3, 4 and 5. So two habits matter for your budget: keep tool results short, and keep the number of steps small. Both come back in the worked example.

A common mix-up

"The model remembers the conversation." It feels true in a chat app because the app does the resending for you. The model itself has no memory: if your program forgot to include an earlier message, the model would behave as if it never happened. Remembering is the program's job.

Check yourself

Your program runs three tool calls and then asks the model for its final answer. The student's original question was 50 tokens and each tool result was 400 tokens. Ignoring the system prompt, tool descriptions and the model's own words, how many tokens does the final call read?

Show the answer

1,250. The final call reads the question and all three results once each: 50 + 400 + 400 + 400.

When the context gets full 5 min

A long agent run keeps adding messages, so sooner or later the desk is crowded: either it hits the window limit, or it gets so full that the model attends poorly and the cost per step climbs. Three standard remedies, in order of effort (all from Anthropic's context engineering post):

RemedyWhat it doesMakerspace example
Clear old tool resultsDrop bulky results the model has already used. Described as one of the safest, lightest forms of compaction.After the booking is confirmed, delete the long manual page that was fetched earlier.
CompactionSummarize the conversation, then start a new context with the summary.A long chat about a 3D-printer jam is summarized to "model, symptom, fixes tried."
Sub-agentHand a side task to a separate model call with its own clean context; it returns only a short summary.Reading ten manuals to compare two machines, then reporting a paragraph.

Compaction has a trap: a summary can drop a detail you needed later. So decide in advance what must survive (for a booking, the machine, date, time and student), and prefer clearing bulky tool results first.

Check yourself

A student chats for an hour about a laser-cutter problem. The context is large but the assistant still works. What is the cheapest sensible change?

Show the answer

Clear old tool results that were already used. It removes the bulk and loses the least.

What is kept between sessions 6 min

A session is one task or conversation, from the first message to the last. When it ends, the context is gone. Nothing carries over to the next one unless your program saves something and loads it back. So Riley's assistant, left alone, has never met any student before: it does not know that Sam finished the laser-cutter training last month.

The fix is the same trick as before, one level up. Save facts outside the context, in a file or a database, and put the relevant ones back into the context at the start of the next session. Anthropic calls one version of this structured note-taking, or agentic memory: the agent regularly writes notes to storage outside the context window, and those notes are pulled back in at later times (Anthropic). A to-do list and a NOTES.md file are everyday examples; this workspace uses one for your tutor.

Two ways to build it

  • Your program does it. After each session, your code writes what matters; at the start of the next, it loads the student's record into the system prompt or the first message. Simple, predictable, cheap.
  • The model does it, through a tool. The model gets a memory tool and decides what to save and read. Claude's memory tool works this way: Claude only requests memory operations such as create, view or delete in a /memories folder, and your application runs them against storage you control (Claude docs, memory tool). It is the agent loop again: a request, your program acts, the result comes back.

For the makerspace, a student's training status is a hard fact that must be right. That points toward a database your program reads through a tool like check_training_record(student), rather than a free-form note the model wrote itself. Save to the model's notes the softer things: "this student prefers morning slots," or "was debugging a print that warped."

A saved note enters the context, so it costs tokens every session it is loaded. Save little, and load only what the current request needs. Also decide what you will never store (such as private details), and when old notes expire; the memory tool docs list size limits, expiry and sensitive data as your handler's job.
A common mix-up

"The model learns from each conversation." It does not. Saving a note changes your storage, not the model. Its training stopped before you ever called it, as you already saw in what a language model does. Memory is files you put back into context; nothing about the model changes.

Check yourself

Pat finishes the 3D-printer training on Monday. On Friday Pat asks the assistant a question in a new session. The assistant answers correctly that Pat is trained. What must have happened?

Show the answer

The status was saved somewhere outside the context on Monday, and loaded into the context in the new session, by the program or by a tool call.

Retrieval: finding the right page 5 min

Now the manuals. The laser cutter's manual might run to hundreds of pages. Pasting it all into every request would be slow, expensive and, because of context rot, often worse. Instead you retrieve: find the few passages that bear on this question and put only those in the context. Retrieval is looking up relevant information from outside the context and bringing it in, so the model can answer from it.

How a manual search typically works

  1. Chunk: split each manual into passages of a few paragraphs.
  2. Index: make each chunk searchable, by keywords, by meaning (using embeddings, numbers that place text with similar meaning close together), or both.
  3. Search: turn the student's question into a query, find the best-matching chunks.
  4. Hand over: put those few chunks in the context and let the model answer, citing the manual.

One known weakness: a chunk cut from a manual can lose its surroundings. A chunk saying "set the power to 40%" does not say which machine or which material. Anthropic's contextual retrieval fixes this by prepending a short description of where the chunk comes from to each chunk before indexing it (Anthropic, contextual retrieval). A cheap version you can do by hand: start every chunk with the machine name and section title.

Two timings

You can retrieve up front, before the model starts, or just in time, as a tool the model calls when it decides it needs a page. Anthropic describes both and notes that Claude Code mixes them: some files loaded up front, others found at run time with search tools, and it advises doing "the simplest thing that works" (Anthropic). For your assistant, a search_manuals(machine, query) tool is just-in-time retrieval: it fits the agent loop you already know, and the manuals only cost tokens when a question needs them.

A common mix-up

"Retrieval means the model searches the manuals itself." The model does not touch your files. It writes a request to a search tool, your program runs the search and returns a few chunks, and only those chunks enter the context. If the search returns the wrong chunk, the model answers from the wrong chunk, so search quality sets your answer quality.

Check yourself

A student asks "What is the cutting speed for 3 mm acrylic on the laser cutter?" Which design is the best fit for a small budget?

Show the answer

Search the manuals and hand over the best few chunks. It keeps the answer grounded in your manual and keeps the tokens per call small.

Worked example and practice 8 min

Worked example

Problem. Sam returns to the assistant: "Book the laser cutter Friday at 3 if I'm trained, and tell me the max material thickness." Decide what is in the context, what is retrieved, and what is saved.

  1. Session start. The program builds the context: system prompt, tool descriptions, Sam's question. It also loads Sam's saved note ("prefers afternoons") because it is short and relevant. It does not load any manual, since nothing says yet which one is needed.
  2. Step 1. The model requests check_training_record("Sam"). The program runs it and appends a one-line result ("laser: trained"). Cost: tiny.
  3. Step 2. The model requests search_manuals("laser cutter", "maximum material thickness"). The program returns the top two chunks, not the manual. Cost: a few hundred tokens, and they stay in context for later steps.
  4. Step 3. The model requests check_calendar("laser cutter", "Friday"), then book(...) after Sam confirms. Each result is a short line.
  5. Final answer. Booking confirmed, thickness limit quoted from the manual chunk. Five model calls, each re-reading the growing history.
  6. Session end. The program saves one line: "Sam booked laser, Fri 3 pm." The training record was already in the database, so nothing is duplicated into notes. The context is then discarded.
Your turn

Priya asks: "My 3D print keeps warping. Last time you told me to heat the bed. What else can I try?" Step 1 is given: the program starts a new session and builds the context. Decide: (a) what the program should load at the start so the assistant knows "last time"; (b) what it should retrieve, and when; (c) what it should save at the end.

Show a solution

(a) Load Priya's saved note from last session ("printing warped parts; advised heating the bed"). The model cannot recall that conversation by itself, so without the note it would not know what "last time" means. (b) Retrieve just in time: when the model decides it needs advice, it calls search_manuals("3D printer", "warping") and gets a few chunks. No manual is loaded up front. (c) Save a short update: "warping; bed heating tried; suggested [new fix from the manual]." Keep it to a line or two, so loading it next time stays cheap.

Summary 2 min

  • The context is everything the model is given for a call; the window is its limit, and you pay for the tokens in it.
  • The model is blank on every call. Within a task, the program resends the history, so cost grows with each step; trim bulky tool results.
  • Between sessions, nothing persists unless you save notes or records outside the context and load them back. The model itself learns nothing.
  • Retrieval finds a few relevant chunks of a long manual and puts only those in the context; a search tool called just in time fits the agent loop.
  • A bigger window is not a reason to stuff it: smaller, high-signal context is cheaper and often better.
