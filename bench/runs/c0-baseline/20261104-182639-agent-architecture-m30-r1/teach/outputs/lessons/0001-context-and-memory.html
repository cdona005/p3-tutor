Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a searchable library, and say why.

Objective O3: context window, memory between steps and sessions, retrieval and notes About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three come down to one skill: choosing what the model sees at each step. That is the decision you will defend at your design review.

The context window 5 min

Start with a concrete case. A student types: "How do I change the blade on the band saw?" Your program sends the model some text and gets text back. What exactly does it send? Not just the question. It sends:

  • the instructions you wrote for the assistant (the system prompt: who it is, its rules, how to behave);
  • the descriptions of the tools it may call;
  • the conversation so far, including the student's question and any earlier tool results.

All of that text together is the context: everything the model can see when it writes its next output. The context window is the limit on how much text the model can take in at once, plus what it writes in reply. Anything outside the window does not exist for the model, however true it is.

The size of the window is counted in tokens. A token is a chunk of text the model reads as one unit: often a short word or part of a longer one. A rough rule for English is that 100 tokens is about 75 words, but the exact count depends on the model's tokenizer. Tokens matter twice: they fill the window, and they are what you pay for. Model providers usually charge per token read (input) and per token written (output), so every extra token you send costs money.

Window sizes change with every model generation, so look up the current number for the model you choose rather than memorising one. Anthropic's engineering team also warns that longer is not simply better: models have a finite "attention budget," so the aim is the smallest set of high-signal tokens that gets the job done (Effective context engineering for AI agents).
A common mix-up

"A bigger window means I can paste in all the manuals and be done." It is tempting because it sounds simple. But you pay for every token on every call, and a window stuffed with mostly irrelevant text gives the model more to sort through. A big window raises the ceiling; it does not make filling it a good idea. You will see the cost next.

Between steps: everything is re-sent 6 min

In the agent loop, each step is a separate model call. The model keeps no state of its own between calls: when a call ends, it forgets. So how does it "remember" that it already checked the calendar? Because your program sends the whole history again on the next call. The history is a list your program keeps, usually a Python list of messages; each loop adds to it and passes it in full.

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # model sees ALL of messages
    messages.append(reply)                               # keep what the model said
    if reply is a final answer:
        break
    result = run_tool(reply)                             # the program runs the tool
    messages.append(result)                              # the result goes into the context

This sketch is pseudocode (not a real library call), but it is the shape of every agent. The messages list is the agent's short-term memory between steps. It lives in your program, not inside the model. It also grows, and that growth is what costs you.

Worked example: what one request costs

Suppose the system prompt and tool descriptions take 1,500 tokens, and the student's question takes 50. The model calls check_calendar (a 40-token request), which returns 300 tokens. It then calls search_manuals (40 tokens), which returns 2,000 tokens. Then it writes its answer. Count the tokens sent as input on each call.

  1. Call 1 sends 1,500 + 50 = 1,550 tokens.
  2. Call 2 sends all of that plus the 40-token request and 300-token result: 1,550 + 40 + 300 = 1,890.
  3. Call 3 sends call 2's input plus another 40 and 2,000: 1,890 + 40 + 2,000 = 3,930.
  4. Total input over the request: 1,550 + 1,890 + 3,930 = 7,370 tokens, even though the new information added was only about 2,400 tokens.

Early content is paid for again on every later call. A big tool result early in a long run is the most expensive kind. Some providers offer prompt caching, which makes re-sent, unchanged text much cheaper; check your provider's pricing for how it works.

A common mix-up

"The model remembers what it did earlier in the request." It does not; your program shows it the earlier steps every time. This matters because you control that list. If you leave something out of messages, the model has never seen it. If you leave something in, you pay for it again.

When the window fills up 4 min

A long run can fill the window, or just become expensive and noisy before it does. The program has three common moves, each a choice about what to keep in messages.

MoveWhat it doesWhat you risk
Clear old tool resultsReplace a bulky result you no longer need with a short stub, such as "manual page 12 was read".The model cannot re-read it, though it can call the tool again.
Summarise (compaction)Ask the model to write a short summary of the run so far, then restart with the summary in place of the history.A detail the summary left out is gone.
Limit tool outputMake tools return only what is needed, such as three matching slots, not the whole calendar.You must decide in advance what "needed" is.

Anthropic describes these as context management for long-running agents: clearing stale tool results as the agent nears the limit, and giving it a memory tool for what must outlast the window (Managing context on the Claude Developer Platform). Their engineering post says tools should return token-efficient information, and lists compaction and external notes as core techniques for long tasks.

For the makerspace assistant, the third move is the cheapest and the first one to try: a check_calendar that returns the free slots for one machine on one day is far better than one that returns the whole month.

Between sessions: notes 5 min

A session is one conversation: it starts when a student opens the assistant and ends when they close it. When it ends, messages is gone, and so is everything in the context. The next day the model starts blank. So how will the assistant know that Jordan finished laser cutter training last week?

Not by keeping the window alive, and not by the model "learning" from the chat: using a model does not change what it learned in training. Memory between sessions is text your program saves outside the window and loads into it later. Think of a lab notebook: the engineer's head is the context, the notebook is the memory. You write down what matters and read it at the start of the next day.

This is called external memory, or notes. It can be as plain as a file or a database row. Anthropic's memory tool works this way: the model reads and writes files in a memory directory that persist across sessions, while the program decides what is loaded back (Memory & context management cookbook).

Worked example: Jordan's training status

Design what the assistant saves for Jordan.

  1. Decide what is worth keeping. Training status and any safety sign-off will matter next visit. The chat's small talk will not.
  2. Save it compactly, for example {"student": "jordan", "trained": ["laser cutter"], "date": "2026-10-28"}. A short record is cheap to load.
  3. Load it at the start of the next session by putting a line such as "Jordan: trained on laser cutter" into the system prompt or the first message.
  4. Treat the official source as the truth. If the trainer's record and the note disagree, the record wins. A note can go stale, and you should plan for that.
Notes can hold anything: a student's habits, a list of broken machines, a summary of an earlier run. Ask of each item: would the next session do worse without it? If not, do not save it.
Check yourself

Next week the assistant must greet Jordan knowing their training. What is the most reliable way to build this?

Show the answer

Save a short record and load it at the start of each session. Memory between sessions is saved text, not something the model keeps.

Retrieval: finding the right page 5 min

Your manuals are too long to paste in, and most of any manual is irrelevant to any one question. Retrieval means: search the library for the few pieces that matter, and put only those into the context. When the retrieved text is added to the model's input to help it answer, the pattern is often called retrieval-augmented generation, or RAG.

Here is a typical setup for the manuals.

  1. Prepare once. Split each manual into chunks of a few paragraphs, keeping the machine name and section title with each one.
  2. Index. Build something a program can search. Two common kinds: keyword search, which matches the words in the question, and embedding search, which turns text into numbers so that chunks with similar meaning score as close even when the words differ.
  3. At question time, search with the student's question, take the top few chunks, and return them as a tool result (search_manuals). The model reads only those.

Retrieval can fail, and the failures are the part to design for. A chunk cut loose from its manual can lose its meaning: a chunk that says "use the speed above" does not say which machine or material. Anthropic's write-up on this problem proposes adding a short note on where each chunk came from before indexing it, and combining embedding search with keyword search; the figures they report are for their own test sets, so treat them as an illustration, not a promise for your manuals. Simple versions of the same fix cost nothing: put the machine name and section title in every chunk.

A common mix-up

"Retrieval is the same thing as memory." They solve different problems. Notes hold what the assistant learned about this student or this run, written by the assistant over time. Retrieval finds facts in a document collection that already exists. Both put text into the context from outside it, which is why they get confused. The test: who wrote it, and when? If the assistant wrote it after the last visit, it is a note; if it came from the manual, it is retrieval.

Choosing where information lives 3 min

Now you have three places to put information. The design question for each item is: how long must it last, and how much of it does the model need right now?

PlaceLastsBest forCost
Context (messages)One sessionThe current question, tool results just fetched, rules in the system promptPaid on every call while it stays
Notes (saved file or record)Across sessionsPer-student facts, preferences, a short run summaryOnly what you load back in
Retrieval (index over documents)As long as the documentsLong manuals, policies, anything too big to load wholeSearch plus the few chunks you return

Notice that live bookings are not on the list. They change by the minute, so you read them with a tool at the moment of need and do not save them as notes. A saved note about "free on Friday" would be wrong by Friday.

Worked example and practice 5 min

Worked example: sort the items

The assistant handles this request: "Book me the 3D printer tomorrow afternoon, the same one I used last time." For each item, say where it lives.

  1. "Which printer I used last time" comes from an earlier session, so it must be a saved note or a booking record, loaded at session start or fetched by a tool.
  2. The 3D printer's free slots tomorrow change quickly, so use a tool call at that moment. The result lives in the context for this session.
  3. How to prepare a print file for that printer comes from a long manual, so it comes from retrieval: a few chunks when the student asks.
  4. The booking rules (limit of two hours, no bookings under 24 hours' notice) are short and apply every time, so put them in the system prompt.
Your turn

The assistant gets this request: "Can I use the CNC router? What speed should I cut acrylic at? I already did the safety course." The first item is done for you: "I already did the safety course" → check the saved training record (a note or a database lookup), and trust the record rather than the student's word.

Now place the other two items yourself: (a) the router's recommended acrylic cutting speed; (b) whether the router is free right now. For each, name the place (context, notes or retrieval), and say what would go wrong if you put it somewhere else. Then, using the token costs from section 2, say why returning one 400-token chunk beats returning the whole 1,500-token manual section.

Show a solution

(a) The cutting speed is a fact in a long manual: retrieval. If you saved it as a note, it would go stale when the manual is revised and the assistant would never see updates. (b) Whether the router is free changes constantly: a tool call, with the result held in the context for this session. A saved note would be wrong by the time it is read. As for chunk size: with an input of 1,650 tokens before the search result, a 1,500-token section makes the last call 3,200 tokens, and a 400-token chunk makes it 2,100. The smaller result is also re-sent on every later call, so it saves again each time the loop continues.

Summary 2 min

  • The model sees only its context: the system prompt, tool descriptions, conversation and tool results. The window limits its size, and tokens measure it and set the price.
  • Between steps, the model remembers nothing. Your program re-sends the whole history on every call, so cost grows with each step. You manage it by clearing old results, summarising and keeping tool output small.
  • Between sessions, memory is text saved outside the window and loaded back in. Keep it short and let the official record win if they disagree.
  • Retrieval finds a few chunks from a large library of documents. Keep each chunk labelled so it still makes sense alone.
  • For every item, ask how long it must last and how much the model needs now.
