Lesson 1 · 30 minutes

Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a library the assistant searches on demand.

Objective O3: context, memory, retrieval and notes About 30 minutes
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three problems are context and memory problems. At your design review you will need to say what the assistant keeps, what it saves and how it finds the right page, with a reason for each.

Warm-up 2 min

Two questions from your agent-loop session. Answer in your head first.

Recall

A student asks, "Is the laser cutter free Friday?" Name the steps of the loop, in order, from the question to the final answer.

Check your answer

The model is called and asks for a tool (say, check_calendar). The program runs the tool. The result goes back to the model. The model is called again and either asks for another tool or writes the final answer. Today's question: when the result "goes back to the model", what exactly does the model receive?

Recall

In that loop, how many times is the model called if it uses two tools before answering?

Check your answer

Three. Every step is a separate model call: one for each tool request, plus one for the final answer. Keep that number in mind; it matters for cost in a few minutes.

The context window 5 min

Start with a concrete case. Priya types: "Can I use the laser cutter on Friday? I've done the safety class." The program sends the model some text and gets text back. Everything the model can use to write its reply must be in the text it was sent. It has no other way to look at the world.

That text is the context: all the tokens the model is given for one call. A token is a small chunk of text, a word or part of a word, which is what models read and write. The context window is the limit on how many tokens the context can hold, including what the model writes in reply. Anthropic's documentation lists what counts toward it: "the system prompt, every message in messages (including tool results, images, and documents), and your tool definitions" (Claude docs: context windows).

So for the makerspace assistant, Priya's call contains these parts:

  • The system prompt: your instructions ("You help students at the makerspace. Never book a machine without checking training.").
  • The tool definitions: the names and descriptions of check_calendar, search_manuals and the rest. The model reads these to choose a tool, so they take space on every call.
  • The messages: Priya's question, and anything that has happened since.
Window sizes differ by model and change often, so look up the current figure for the model you choose rather than memorising one. What stays true is that the window is finite and that you pay for what you put in it.
Check yourself

Your team writes a long, detailed description for each of ten tools. Where do those descriptions take up room in the window?

Show the answer

On every model call. The definitions are sent with each request, so they count toward the window each time. This is one reason to keep tool descriptions clear and the toolset small.

What is kept between steps 5 min

Now the key question for an agent. After the program runs check_calendar, the model is called again to read the result. Does the model "remember" that it just asked for the calendar?

No. The model does not carry anything over from one call to the next. What carries over is the message list that your program keeps and resends. The documentation says each turn's input "contains all previous conversation history plus the current user message", and that the output "becomes part of the input for the next turn" (Claude docs: context windows). The model's "memory" within a task is a Python list that your code appends to.

Worked example: Priya's request, call by call

Assume the system prompt and tool definitions together take 1,500 tokens, Priya's question 30, each tool request 40, the calendar result 200 and the manual search result 3,000. Count the input of each call (these numbers are invented, to show the pattern):

  1. Call 1. Input: 1,500 + 30 = 1,530 tokens. The model asks for check_calendar.
  2. Call 2. The program appended the request (40) and the calendar result (200). Input: 1,530 + 240 = 1,770. The model asks for search_manuals.
  3. Call 3. The program appended another request (40) and the manual pages (3,000). Input: 1,770 + 3,040 = 4,810. The model writes the final answer.

Total input processed: 1,530 + 1,770 + 4,810 = 8,110 tokens, though the conversation itself is only about 3,300 tokens of new content. Early material is paid for again on every later call.

Two consequences matter for your budget:

  • Cost grows with each step. Every extra tool call means another model call, and each call re-sends everything so far. Long tool results are paid for again and again.
  • Your program decides what the model sees. Because you build the list, you can shorten it. The lightest technique is tool result clearing: once the model has used a bulky result, replace it with a short placeholder. Anthropic describes this as one of the safest ways to trim, because a result that has already been used is rarely needed in raw form (Effective context engineering for AI agents).
A common mix-up

"The model remembers the conversation, so I only need to send the new message." It feels true because a chat app seems to remember you. But the model itself keeps nothing between calls. The app resends the history every time. If your code sends only the newest message, the model has no idea what was asked before. Check by thinking of Call 2 above: if the program left out the question from Call 1, the model would not know who is asking or about what.

Check yourself

A manual search returns 3,000 tokens, and the model needs three more steps afterwards. Roughly how often is those 3,000 tokens sent to the model, if nothing is cleared?

Show the answer

Four. The result is appended after the tool runs, so the next call (which reads it) includes it, and so do the three calls after that, if nothing is cleared. That is why clearing bulky results you no longer need saves money.

Why more context is not better 4 min

If cost were the only problem, a huge window would solve everything: put all the manuals in and be done. Two things stop that.

First, cost, as you just saw. Second, quality. The documentation says: "As token count grows, accuracy and recall degrade, a phenomenon known as context rot. This makes curating what's in context just as important as how much space is available" (Claude docs: context windows). Anthropic's engineering team describes the model as having an "attention budget" that every new token uses up a little, and states the goal as "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome" (Effective context engineering).

Think of a workbench. You could pile every tool and drawing for every machine on it, and everything would be "available". You would also work slower and grab the wrong thing. A good bench holds what the current job needs, and the rest stays in the drawer, labelled.

That idea, context engineering, is the name for deciding what goes on the bench: "the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference" (Effective context engineering). The next two sections are its two main tools: notes for what must outlive the window, and retrieval for what should wait in the drawer until needed.

A common mix-up

"A bigger context window means I don't need to manage context." It is tempting because the limit is the visible problem. But a window that is not full can still hold too much: more tokens cost more on every call and, per the documentation, can lower accuracy. A bigger window raises the ceiling; it does not remove the need to choose what goes in.

What is kept between sessions: notes 6 min

A session is one run of the assistant for one conversation. When it ends, the message list is gone, unless your program saved it. So when Priya returns next week, the assistant starts with an empty list. It does not know she finished the laser safety class unless something puts that fact back.

The fix is to give the assistant memory in the practical sense: information stored outside the context window, and loaded into it when needed. Anthropic calls one form structured note-taking: "the agent regularly writes notes persisted to memory outside of the context window. These notes get pulled back into the context window at later times", for example a to-do list or a NOTES.md file (Effective context engineering). In their example, an agent playing a game kept notes such as how many levels a character had gained toward a target, and after its context was reset it "reads its own notes and continues."

Two ways to build it

Anthropic's memory tool shows the pattern. It stores memory as files in a /memories directory, and it is client-side: "Claude requests file operations, and your application runs them" (Claude docs: memory tool). This is the same loop you already know. The model asks to create or view a file, your program does it and returns the result. Your code decides where the files really live, such as a folder per user or rows in a database. The commands include view, create, str_replace, insert, delete and rename.

The alternative is simpler and, for your project, probably better to start with: your program, not the model, writes a small student record (a dict saved as JSON) and loads the relevant fields into the system prompt at the start of each session. Model-written notes are flexible; program-written records are predictable and cheap to check. Both put the facts outside the window and bring them back.

What to save, and what not

InformationWhere it belongsWhy

The full text of the laser cutter manualLibrary, searched on demandLarge; shared by all students; not about Priya
Whether the cutter is free on FridayFetched fresh by a toolChanges constantly; a saved copy goes stale
The raw 3,000-token search result already usedCleared or droppedThe answer drawn from it is enough

Note the third row. Saving something that changes, like calendar availability, creates a stale copy that the assistant may trust. Save facts that stay true; fetch facts that change.

The memory tool's own documentation warns that you must validate file paths, because a request such as /memories/../../secrets.env could otherwise reach files outside the memory folder, and it recommends size limits and expiry for old files. Anything saved about students is also personal data, so save the minimum.
A common mix-up

"If the assistant helped Priya last week, it will recall that this week." It will not, unless your program saved something and loaded it again. Nothing is remembered by default, and saved information the model never receives is as good as lost. Memory is two jobs: write the fact down, and read it back into the context at the right time.

Check yourself

Which fact is the best candidate to save for the next session?

Show the answer

The lathe safety test result. Save small facts that stay true and matter later. Fetch fast-changing facts live, and let bulky tool output go once it has been used.

Retrieval: finding the right page 5 min

Your manuals are far too long to place in every call: you would pay for them each time, and context rot would hurt. So they stay outside the window, in a library, and the assistant brings in only the pages it needs. Retrieval means finding relevant material in stored data and placing it in the context.

Anthropic's article describes two timings (Effective context engineering):

  • Up-front retrieval. Before the model is called, the program searches the library with the student's question (the article names embedding-based search for this) and puts the best matches in the context. One model call, but the program must guess the right pages in advance.
  • Just-in-time retrieval. The agent keeps "lightweight identifiers (file paths, stored queries, web links, etc.)" and uses tools to load data when it needs it. Your search_manuals tool is exactly this. The trade-off the article names: "runtime exploration is slower than retrieving pre-computed data", because each lookup is another step.

A hybrid is common, and the article's advice is to "do the simplest thing that works."

How a manual search works

A typical design splits each manual into chunks (a few paragraphs each, ideally one topic), turns each chunk into a list of numbers called an embedding that captures roughly what it is about, and stores them. A question is turned into numbers the same way, and the chunks whose numbers are closest are returned. This lets "how do I stop the cutter if it catches fire?" find a section titled "Emergency procedures" even though the words differ. A plain keyword search, like grep, is simpler and works well when students use the manual's own words, such as a part number. For your first version, start with the simplest search that passes your test questions.

Whatever the search, three design choices decide your costs:

  • Chunk size. Too large and each result drags in unrelated text; too small and an answer is split across chunks.
  • How many results to return. Each returned chunk lands in the context and is resent on every later call. Return the top three, not the top thirty.
  • What the chunk carries. Include the manual and section name, so the model can say where an answer came from and a student can check it.
A common mix-up

"Retrieval means the model looks things up in the manuals itself." The model only writes a request, for example search_manuals("laser cutter focus"). Your program runs the search and puts the results into the context. If the right page is not in what comes back, the model cannot see it, which is why chunking and search quality are your design decisions.

Check yourself

Retrieval returns 20 manual chunks for every question, 500 tokens each, and the model then makes two more tool calls. What is the most direct fix for cost?

Show the answer

Return fewer, better chunks. Twenty chunks of 500 tokens is 10,000 tokens that are sent on every call from then on. Three chunks is 1,500.

Worked example and practice 5 min

Worked example: sort the information for one request

Priya returns and asks: "Book me the laser cutter Friday at 3 and tell me what material settings to use for 3 mm plywood." Decide where each item lives.

  1. Her training status. Needed before booking; small; true until it changes. Keep it in a saved record. At session start, load it into the system prompt as one line: "Priya: laser training completed 3 Oct."
  2. The Friday 3 pm availability. Changes constantly. Do not save; call check_calendar live. Keep the short result in context until the booking is made.
  3. Plywood settings. They are in a long manual shared by everyone. Keep the manual in the library; call search_manuals and return the top three chunks, with section names.
  4. After the answer. The raw chunks are no longer needed. Clear them, or let the session end. Write one new line to the record only if something worth keeping happened, such as "booked laser, Fri 3 pm".

Result: the window holds the instructions, tool definitions, one record line, one calendar result and three chunks. That is small, current and traceable.

Your turn

Tomas asks: "Last month I told you I'm left-handed and need the left-hand vise. Can I use the drill press on Tuesday, and what's the maximum bit size?" The system prompt and tools are already in place. Sort these four items: (a) his left-handed vise preference, (b) the drill press's Tuesday availability, (c) the maximum bit size from the manual, (d) his drill press training status. For each, say where it lives (saved record, live tool call, or searched library) and one reason. The first is done: (a) saved record, because it is a small stable fact about Tomas that matters in later sessions.

Show a solution

(b) Live tool call: availability changes constantly, so a saved copy would go stale. (c) Searched library: it lives in a long manual shared by all students, so retrieve only the passage that states the limit, and keep the section name so it can be cited. (d) Saved record: it is a small fact that stays true, and it must be checked before booking. Note that (a) and (d) are both loaded at session start, so the model can use them without a search.

Summary 3 min

  • The context window is everything the model reads and writes in one call: system prompt, tool definitions, messages and tool results. It is finite, you pay for it, and too much of it hurts accuracy (context rot).
  • Between steps, the model keeps nothing. Your program keeps the message list and resends it each call, so early material is paid for again and bulky results should be cleared once used.
  • Between sessions, nothing survives unless you save it. Notes or records live outside the window, and must be loaded back in.
  • Retrieval keeps long documents in a library and brings in only the best few chunks, either before the call or just in time through a tool.
  • Rule of thumb: save facts that stay true, fetch facts that change, retrieve what is long and shared, drop what has been used.

Say it in your own words: without looking back, explain to a teammate why the assistant will not remember Priya next week, and what you would add so that it does.
