Context and memory in an agent

By the end of this lesson you can decide, for one makerspace assistant request, what goes in the context window, what gets saved between sessions, and how the assistant finds the right page of a long manual, and you can defend each choice by its token cost.

Objective O3: context and memory in an agent About 30 minutes Builds on: what a language model does, and the agent loop (your earlier sessions)
Why this matters for you

This is the third success criterion of your mission: decide what the assistant keeps in its context, what it saves between sessions, and how it finds the right page in a long manual. It is also where your small model budget is won or lost, because every token in the context is paid for again on every step.

Start here: a failure, then two recall questions 3 min

A student types: "How do I change the bit on the drill press?" Your assistant answers with the steps for the milling machine. The model did not "get confused" in any mysterious way. It wrote the most likely answer from the text it was given, and the drill press manual was not in that text.

So the useful question is never "what does the model know?" but "what text did it have in front of it on that call?" Context and memory are the answer to that question: what you put in front of the model, what you keep for later, and what you fetch only when needed. Each choice costs tokens, and tokens are your budget.

Two recall questions first. They are about the loop you already sketched, and today depends on both.

Recall 1

In the agent loop, who actually runs a tool: the model or the program around it?

Check your answer

The program. The model only writes a request such as "call the calendar tool with these arguments". Because the program runs the tool and decides what goes back to the model, the program controls what the model gets to see. That control is the subject of this lesson.

Recall 2

What does a language model know when it writes its next piece of text?

Check your answer

Two things: what it learned in training, and the text it is given on that call. Nothing else. Today's lesson is about the second part: what that given text is made of, how much of it you can afford, and where it comes from.

The context window: everything the model sees in one call 6 min

You want the assistant to answer a question about the laser cutter. Where must the laser cutter text be for the model to use it? Not on disk, not in the booking database, not "in the system". It must be in the text sent with that call.

Models read and write in tokens. A token is a chunk of text, roughly a word or a part of one. "Laser" is probably one token; a long or unusual word such as an error code may split into several. You never count them by hand; the API reports them. What matters is that tokens are the unit of both the limit and the bill.

The context window is all the tokens the model is given for one call, plus the tokens it writes in reply. The Claude API docs describe it as the model's working memory for that call, separate from its training data, and they list what counts toward it: the system prompt, the messages, the tool definitions and the tool results (Context windows, Claude API docs). The window is finite, and if a call exceeds it the API returns an error or stops generating (same page). Real windows are large: that page lists sizes from 200,000 tokens up to 1 million, depending on the model. So a 30,000-token result will not overflow a window. It still costs money and, as section 2 shows, quality.

The primary source for this lesson treats this limit as the central design fact: context is a finite resource, so the question is always which tokens are worth including (Effective context engineering for AI agents).

What is in one window

For the makerspace assistant, one call carries these parts. The token counts are illustrative estimates, not measurements.

PartWhat it isEstimate
System promptYour fixed instructions: role, rules, tone400
Tool definitionsNames, descriptions and arguments of each tool600
Student questionThe message that started the request30
Tool resultA 40-page PDF manual returned by a tool30,000

The history is the running list of everything so far in the conversation: the question, each tool request the model made, each tool result, and the model's own earlier replies. Your program keeps it as a list and passes it to every call. In pseudo-Python:

messages = [{"role": "user", "content": question}]

while True:
    reply = call_model(system=SYSTEM_PROMPT,
                       tools=TOOL_DEFINITIONS,
                       messages=messages)      # the model sees only this
    messages.append(reply)                     # its own output joins the history
    if reply.wants_tool:
        result = run_tool(reply.tool_call)     # the PROGRAM runs the tool
        messages.append(result)                # now the model can see it
    else:
        break

Read the last lines carefully. The tool result is visible to the model only because the program appended it. If the program does not append something, the model has no way to reach it.

Analogy for you as a programmer: the window is like a fixed-size buffer in RAM that your program fills before each call. It breaks down in one place: the model does not read the buffer by address. It attends to all of it at once, and, as the next section shows, not equally well.
A common mix-up (M1)

"The model can look things up in the booking database or the manual folder on its own." It is tempting because the loop says the model "asks" for tools, which sounds like it reaches out. It does not. It writes a request; your program runs it and decides whether and how the result is appended. Data the program never appends does not exist for the model.

Between steps: the history grows, and so does the bill 6 min

A booking request takes six calls. In call 1 the assistant fetches a 30,000-token manual page. What does call 6 cost?

If you assumed "just the new text", look at the loop again. The model keeps nothing between calls. Each step is a fresh, separate model call. So the program re-sends the whole history every time, and the Claude API docs say the same: each turn re-sends prior history, so tokens accumulate (Context windows).

The re-sending table

Here is that request, ignoring the model's own short outputs to keep the numbers clean (estimates). The start is 1,030 tokens: system prompt, tool definitions and the question.

The new text over the whole request is only 33,530 tokens. The input you pay for is 163,180, nearly five times that, because the manual page is sent in calls 2 to 6, five times. In CS terms, the total is the sum of a growing prefix. One big result costs its size times the number of later calls; if every step adds a similar amount, the total grows with the square of the number of steps.

Prompt caching, where the provider reuses an unchanged start of the input at a lower price, can discount re-sent tokens. The tokens still fill the window and dilute recall, so clearing stays worthwhile. Check current pricing.

A common mix-up (M3)

"Each step only costs its new text." The loop looks incremental, so this feels natural. The table shows otherwise: the manual page is billed again at every later call until something removes it from the history.

More context is not better context

Maybe the answer is a bigger window and everything in it. The evidence says no. The primary source calls this context rot: as the number of tokens grows, the model's ability to recall from them tends to drop, so context has diminishing returns and works like an attention budget (Effective context engineering). The Claude docs say the same about accuracy and recall (Context windows).

One peer-reviewed study tested this. On question answering and key-value lookup, performance was often highest when the relevant text was at the start or the end of the input, and dropped when it was in the middle, even for models built for long contexts (Lost in the Middle, Liu et al., TACL 2024). A manual page buried in the middle of 30,000 other tokens may be in that weak spot.

A common mix-up (M5)

"A bigger window means the assistant can load everything, and more context means better answers." Larger windows are advertised, so it is tempting. But more tokens cost more on every call, and the model may use the middle of them worse. Size is a limit, not a quality guarantee.

Two ways to keep the history small

  • Clear old tool results. After call 2 the model has used the manual page: it has written the settings into its reply. Remove the 30,000 tokens from the list. Figure 2's second set of bars shows the effect: calls 3 to 6 drop by 30,000 each, and the total falls from 163,180 to 43,180.
  • Compact. When a long conversation nears the limit, summarize it and start a new window with the summary. This is compaction, and the primary source names it as a core technique for long tasks (Effective context engineering).

Clearing is a small edit to the list your program already holds. Check the token usage the API reports, and when it passes a threshold you choose, replace old results:

for m in messages:
    if m.is_tool_result and m.age > 2:
        m.content = "[manual page removed; search again if needed]"

Compaction is lossy compression, like saving an image as a small JPEG. A summary that drops a detail cannot give it back. So summarize by priority: keep decisions and open commitments (the user chose Friday afternoon; the booking is not yet confirmed), and drop raw output that you can fetch again (the manual page).

Between sessions: a new session starts empty, so write notes 5 min

A student returns a week later and asks: "Am I cleared for the laser cutter?" The assistant has no idea who they are. Why not? The student passed the training last week, in this very assistant.

A session is one run of the assistant from the first message to the end of the conversation. When it ends, its message list is gone. A new session builds a new list, containing the system prompt, the tool definitions and the new question, and nothing else. In process terms, it is a restart: all the RAM is lost.

Two common mix-ups (M2, M4)

M2: "The model learns from each chat and remembers the student next time." Chat apps seem to remember you, which makes this tempting. But using a model does not change it: a call reads the model's weights and never writes them. The memory tool docs show where memory really lives: in your own application, outside the model (Memory tool). What a chat app calls memory is something its program saves and sends again.

M4: "The context window is a place that persists, like a saved document." It is rebuilt on every call and discarded at the end of the session. Only the program can save things beyond that.

Memory in an agent means information stored outside the window, by the program, so that it can be loaded into a later window. It is the disk to the window's RAM. The primary source calls the pattern structured note-taking: the agent writes notes to storage outside the context and reads them back later (Effective context engineering).

The Claude API memory tool shows one concrete way to do it. The model creates, reads, updates and deletes files in a /memories directory through tool calls, and the application runs those operations, so the storage lives in your system and you control it. The docs describe a multisession pattern: read the progress notes at the start, update them at the end (Memory tool, Claude API docs).

A note file in practice

For the makerspace, one file per student, notes/student_4821.md:

- Laser cutter training passed 2026-11-09.
- Prefers evening slots.
- Open booking: laser cutter, Fri 2026-11-20, 14:00.

The program does two jobs around the model:

def start_session(student_id, question):
    notes = load_notes(student_id)          # read the file from disk
    system = SYSTEM_PROMPT + "\nStudent notes:\n" + notes
    return [{"role": "user", "content": question}], system

def save_note(student_id, line):            # exposed to the model as a tool
    append_to_file(f"notes/{student_id}.md", line)

Now the returning student's question can be answered from the first call, because the notes are in the window. Save as you go, not only at the end: a session that crashes before its last step otherwise loses everything it learned.

What to save, and what not to

  • Save: facts that are small, that you cannot re-fetch, and that stay useful: training status with a date, stated preferences, open bookings.
  • Do not save: raw manual text (large, and the manual can be searched again), and anything that goes stale quickly, such as which slots are free.

Two limits matter.

  • Size. The memory tool docs advise capping file size and expiring old memories (Memory tool). A note file that grows without bound just rebuilds the problem of section 2, loaded at every session start. Keep notes short, delete expired lines, and once a student's notes get long, search them with the same kind of search tool section 4 describes instead of loading them all. That is where notes and retrieval meet.
  • Trust. You have already seen a chatbot state an outdated fact with confidence. A stale note does the same. "Open booking: Friday" in a note, read two weeks later, is confidently wrong. Date your notes so the model, or your code, can judge them.
Frameworks call memory within one conversation short-term and memory across conversations long-term (LangGraph memory overview). The split that matters here is window versus saved file.
A common mix-up (M6)

"Memory is just a bigger window." Both feel like "what the model remembers", so they blur together. They differ in cost and in lifetime. The window is per call, billed on every call (caching aside) and wiped at the end. Memory sits outside, costs nothing until loaded, and you choose which parts to load.

Retrieval: finding the right page without loading the whole manual 5 min

A student asks about error E-47 on the 3D printer. Suppose, for illustration, your makerspace manual set is 4 million tokens. No window holds that, and even loading a slice of it on every call would use up the budget quickly. (Measure your real set before you decide; it may be much smaller.) How does the assistant find the one page that matters?

Retrieval means finding the few pieces of stored information that are relevant to the current question and putting only those into the window. You already know the data-structure version: an index lookup instead of a full table scan.

Upfront or just in time

There are two ways to give the model the manuals:

  • Load everything upfront. Simple, but you pay for every token on every call, and the model may use the middle of it poorly.
  • Just in time. The window holds only light references, such as file names and a search tool, and the model loads the pieces it needs with tool calls. The primary source describes this as keeping lightweight identifiers and loading data at run time, and says the most effective agents might use a hybrid of both (Effective context engineering).

How a search tool works

(The number of chunks returned is a tunable trade-off between cost and recall. The Contextual Retrieval post found 20 chunks worked better than 10 or 5 and advises testing for your own case; 3 here is only for round numbers.)

For a long manual set, the usual design splits each manual ahead of time into chunks: small pieces, such as one section or a few paragraphs. A search tool then returns the best matches for a query, and only those go into the window. In pseudo-Python the model sees a tool like this:

search_manuals(query: str, machine: str) -> list of 3 chunks
# each chunk is about 500 tokens, so 1,500 tokens come back
# instead of 30,000 or more for a whole manual

There are two ways to match. Keyword search finds chunks containing the exact string, and is best for things like error codes. Meaning-based search finds chunks that say something similar even in different words; it works by turning text into lists of numbers called embeddings and comparing them, and you do not need the math for this course. The Anthropic retrieval post describes using both: embeddings for meaning, a keyword method (BM25) for exact terms such as error codes, merging the results and putting the top few chunks in the prompt (Introducing Contextual Retrieval).

A question such as "my print will not stick to the bed" has no exact string, so meaning search helps. "E-47" is an exact string, and meaning-based search may rank it poorly because the code carries little meaning. Keyword search finds it directly.

The trade-offs

  • Retrieval can miss. If the search returns the wrong chunk, the model may still answer confidently from it. Return the manual name and page with each chunk so the answer can cite it, drop matches below a minimum score, and tell the assistant to reply "no match found" instead of guessing. Check a sample of real questions against the right pages.
  • Chunks lose context. A chunk that says "set speed to 4 mm/s" may not say which machine it describes. Store the machine and section title with every chunk, and filter by machine. The Contextual Retrieval post is about exactly this problem.
  • Skip retrieval when you can. The same post says a knowledge base under about 200,000 tokens, roughly 500 pages, can go straight into the prompt with no retrieval, and that prompt caching can cut the cost (Contextual Retrieval). A small, stable manual set that every call needs may not justify a search tool.

An illustrative 4-million-token set is far over that line, so retrieval fits it. If your real set is under the line, skip retrieval. It is a trade-off, not a rule: the answer depends on the size of the material, how often it is needed and what the bill allows.

When the whole set is small enough to fit comfortably (the post's rough line is about 200,000 tokens), is reused across calls, and the cost is acceptable. Then loading it is simpler and has no risk of retrieving the wrong chunk.

Worked example and practice 5 min

Now use all four ideas on one request. The design has five steps: (1) what the window starts with, (2) what each tool call returns and costs, (3) what to clear, (4) what to write to notes, (5) the total tokens, counting re-sends. All token counts are estimates.

Worked example

Request: "Book me the laser cutter Friday afternoon, and remind me what I still need for certification."

  1. Start of the window. System prompt 400, tool definitions 600 (calendar, booking, manual search, save note), the student's notes loaded at session start 150, the question 30. Total 1,180. The notes are why the assistant knows who this is before any tool call.
  2. Tool calls and results. Call 1: check the calendar for Friday, a result of 600 tokens. Call 2: search_manuals("laser cutter certification requirements"), three chunks, 1,500. Call 3: book the slot, 100. Call 4: save a note, 20. Call 5: write the final answer. Searching returns 1,500 tokens, where loading the 40-page manual would return 30,000.
  3. What to clear. After the booking in call 3, the full calendar result (600) has done its job: the decision, "Friday 14:00 booked", is what matters. Clear it. Keep the three chunks, because the final answer needs the certification steps in them.
  4. What to write to notes. One dated line: "2026-11-16: booked laser cutter Fri 2026-11-20 14:00; still needs the safety quiz." Do not save the chunks or the calendar listing: both are re-fetchable, and the calendar goes stale.
  5. Cost with re-sending. Call inputs: 1,180; 1,780; 3,280; then, after clearing the calendar result, 2,780 and 2,800. Total 11,820 input tokens. Without clearing it would be 13,020. Had the whole manual been loaded upfront, every one of the five calls would carry 30,000 more, 150,000 extra in all.

Summary 3 min

  • The model sees only the context window: the tokens your program sends on one call. Anything not appended to it does not exist for the model.
  • The program re-sends the whole history every step, so cost grows with every added result. Clear what is used and re-fetchable; compact by keeping decisions and open items.
  • A new session starts empty. Memory is a file the program saves and reloads; save small, dated facts, never raw manuals.
  • Retrieval puts only the best chunks in the window: keyword search for exact strings, meaning search for paraphrases. Below roughly 200,000 tokens, loading everything can be fine.

Say it in your own words: explain to a teammate why the assistant forgets a student between visits, and what you would save so it does not. Do it without looking back, then compare.
