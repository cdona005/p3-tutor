## The win
By the end, Riley can decide, for one makerspace assistant request, what goes in the context window, what gets saved between sessions, and how the assistant finds the right page of a long manual, and can defend each choice by its token cost.

**Mission tie:** this is the mission's third success criterion ("decide what the assistant keeps in its context, what it saves between sessions, and how it finds the right page in a long manual"), and it ties to the small model budget, since every token in context is paid for on every step.

## Ideas the lesson teaches
The objective's ideas, and which get a section:
1. Context window = all the tokens the model is given for one call (system prompt, tool definitions, history, tool results, its own earlier output); a token is a chunk of text; the window is finite and what is in it is billed (S1). Full depth.
2. Between steps: the model keeps nothing itself; the program re-sends the whole history each step, so context grows and cost grows with it; more context is not better (context rot, Lost in the Middle); what to do: clear old tool results, compact by summarizing (S2). Full depth, with the trade-off (summaries lose detail).
3. Between sessions: a new session starts empty; anything to survive must be saved outside the window by the program; notes as memory, written and read through tool calls (memory tool pattern), what to save and what not, size caps and expiry (S3). Full depth.
4. Retrieval: just-in-time (keep light references, fetch with a tool) versus loading everything upfront; chunk-and-search for a long manual; keyword search for exact terms (error codes) versus meaning search; skip retrieval when the manual set is small (under about 200k tokens per the Contextual Retrieval post) (S4). Full depth on the just-in-time idea and the trade-off; embeddings and reranking get one or two lines, defined in plain words.

**Left out:**
- Sub-agents returning condensed summaries: it belongs to the multi-agent objective; one pointer line in the summary only.
- Memory taxonomy (semantic, episodic, procedural) and hot-path versus background writes: vocabulary, not needed for the win; at most a margin note in S3.
- Embedding math, reranking internals, chunking strategies in depth, prompt caching details: out of scope per the mission (no model math); a later retrieval lesson can take them.
- Writing code that calls a model: not yet taught; use pseudo-Python only for what the program does around the model.

## Where the learner starts
- Skip: what a model does (record 0001) and the loop at a high level (record 0002). Build on them, do not re-teach.
- Does not know: tokens, context window, why they limit and cost, memory, retrieval. Teach "token" in S1 in one sentence, before any other section uses it.
- Quiz 0001 (loop and tool calling) is ungraded and unchecked on two points: the program, not the model, runs each tool, and every step is a separate model call. This lesson depends on both, so S1 restates them as the base of "re-sent each step" and the warm-up recalls them.
- Preferences: concise first, bullets, computer-science examples, direct tone, no praise in feedback, give reasoning only for what is wrong or needed. Practice feedback: state the right answer, say why each wrong option fails, no encouragement.
- Use the makerspace assistant as the running case (machine manuals, booking calendar, per-student training status), framed in CS terms: the context window as a fixed-size buffer/RAM, the saved notes as disk, retrieval as an index lookup versus a full table scan, compaction as lossy compression, a new session as a process restart. Say where the analogy breaks (the model does not read "RAM" by address; it attends to everything in the window, imperfectly).

## Warm-up (reveal on demand)
1. In the loop, who actually runs a tool, the model or the program? (Program; the model only asks.) Why it matters here: the program decides what to put in front of the model.
2. Per record 0001: the model knows only what? (Its training plus the text it is given.) This sets up "context is everything it is given".

## Misconceptions
- M1: "The model can look things up in the program's data or the manual on its own." Tempting because the loop talks about tools and the model "asks". Named in S1. Show: only what the program appends to the message list is visible.
- M2: "The model learns from each chat and remembers the student next time." Tempting from experience with chat apps that seem to remember. Named in S3. Show: weights do not change; memory is a file the program reloads.
- M3: "Each step only costs the new text." Tempting because the loop looks incremental. Named in S2. Show: the table where the 30k manual page is billed in every later step.
- M4: "The context window is a place that persists, like a saved document." Tempting from long chat histories in apps. Named in S3. Show: a new session has an empty window; the figure.
- M5: "A bigger window means the assistant can just load everything, and more context always means better answers." Tempting because larger windows are advertised. Named in S2 and S4. Show: context rot, Lost in the Middle (middle text used worse), and the bill. State the trade-off, not an absolute: below about 200k tokens, loading everything can be a sound choice.
- M6: "Memory is the same as a bigger window." Tempting because both are "what the model remembers". Named in S3. Show: window is per call and billed; memory is stored outside and loaded selectively.
(Use these ids for the quiz keys' distractors; the learner's files hold no earlier misconception ids, so keep M1 to M6 stable.)
