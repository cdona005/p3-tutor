Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in a saved note, or in a searchable store, and say why.

Why this matters for you

Your assistant must answer from long machine manuals, and remember each student's training status between visits, on a small budget. Those are three context-and-memory decisions, and you will defend them at your design review. Each one changes what a request costs.

The program around the model runs the tool. It then adds the result to the conversation and calls the model again. That "adds to the conversation, calls again" step is exactly what this lesson examines: the conversation is the model's only view of the world.

Recall

A language model produces text one token at a time. In one sentence: what is a token, roughly?

Check your answer

A token is a chunk of text, often a word or part of a word, that the model reads and writes. Tokens are the unit that context limits and prices are counted in.

The context window 5 min

A student asks your assistant a question. What does the model actually know when it answers? Not what the student said last week, and not the whole manual library. It knows only what is in the text sent in this one call.

That text is the context: everything the model is given for one call. It usually holds the system prompt (the assistant's rules), the tool descriptions, the conversation so far, and every tool result. The context window is the maximum number of tokens the model can handle at once, input and output together (Claude docs: context windows).

Think of it as the model's working memory, like the variables in scope in a function. Anything not passed in does not exist for that call. The analogy stops here: a function keeps its variables between lines, but a model keeps nothing between calls. The program must pass everything in again.

A bigger window is not simply better. Anthropic's docs describe context rot: as the token count grows, the model's accuracy and recall degrade (Claude docs). Anthropic's engineering team frames the goal as finding the smallest set of high-signal tokens that gives the outcome you want (Effective context engineering for AI agents).

A common mix-up

"A huge window means I can paste in every manual and skip the design." It is tempting because it removes work. It fails twice: every token you send is a token you pay for, on every call, and a crowded context makes the model worse at finding the one relevant line. With a small budget, the window is something to spend carefully, not something to fill.

What is kept between steps 6 min

Inside one request, the agent loop calls the model several times. Does the model remember step 1 when it reaches step 3? Only because the program re-sends it. Each call carries the full history so far: the question, every earlier tool request and every tool result. The Claude docs describe this as linear growth, with previous turns preserved completely (Claude docs).

That has a cost consequence you can compute. Input is billed per token on every call. A step that adds 600 tokens to the history is not paid for once: it is re-sent, and paid for, on every later call. So the total input across a request grows faster than the final context size.

Worked example (illustrative numbers)

The assistant starts with 2,000 tokens (system prompt, tool descriptions and the question). It makes four model calls: three tool steps, then the final answer. Each tool step adds 600 tokens (the request plus the result). How many input tokens are sent in total?

  1. Call 1 sends 2,000 tokens.
  2. Call 2 sends 2,000 + 600 = 2,600, because step 1's request and result are now in the history.
  3. Call 3 sends 2,000 + 1,200 = 3,200.
  4. Call 4 sends 2,000 + 1,800 = 3,800.
  5. Total input: 2,000 + 2,600 + 3,200 + 3,800 = 11,600 tokens, even though the final context is only 3,800.

Two levers follow. First, keep the fixed top block short, since it is paid for on every call. Second, keep tool results small: a tool that returns a whole manual chapter instead of the relevant paragraph is paid for again on every later step. Anthropic's advice is that tools should return token-efficient output (Anthropic engineering).

Many providers offer prompt caching, which makes repeated identical prefixes cheaper. Check your provider's pricing before you rely on it in the design review; this lesson does not cover it.

What is kept between sessions 4 min

Your assistant must know that a student finished laser cutter training last month. When that student returns tomorrow, where does that fact live? Not in the model, and not in the context, since a new session starts with an empty history.

So persistence is your program's job. The pattern is plain engineering: write the fact to storage you control, such as a database row or a JSON file, and load it when a session starts or when a tool asks for it. Call anything the agent can read back later memory. Memory in an agent is just storage plus a rule for when to read and write it.

Not everything should be saved. Save facts that stay true and that the assistant would otherwise have to ask for again: training completed, preferred machines. Do not save every message. A transcript grows without bound, and loading it back into the context would bring back the same cost and context-rot problems from the previous sections.

A common mix-up

"Chat apps remember me, so the model must remember." Those apps save your history and send it back to the model each time; the model itself does not change between calls. For your assistant, you build that save-and-load step yourself.

Retrieval: finding the right page 6 min

The laser cutter manual is 200 pages. A student asks what to do when the lens is dirty. Sending all 200 pages every call is wasteful and, as above, hurts accuracy. What is the alternative? Fetch only the few passages likely to answer the question, and put those in the context.

This is retrieval, and using it to feed a model is called retrieval-augmented generation (RAG). The usual setup has two phases:

  • Before any question (indexing): split each manual into chunks of a few paragraphs and store them in a searchable index.
  • At question time (search): turn the question into a query, find the best-matching chunks, and place only those in the context, so the model answers from them.

"Best-matching" can mean two things. Keyword search, such as BM25, finds chunks sharing exact words with the query: good for a part number like "M3-LS-204". Embedding search compares meaning: it should connect "dirty lens" to a paragraph titled "Cleaning the focusing optics". Anthropic's tests found that combining both beat embeddings alone (Anthropic: contextual retrieval).

Retrieval has a failure mode: a chunk cut out of its manual may lose its subject. "Replace it every 500 hours" says nothing about which part. Anthropic's fix is to have a model prepend a short, chunk-specific explanation to each chunk before indexing, which cut failed retrievals in their tests from 5.7% to 3.7% with embeddings, and to 2.9% when combined with keyword search (Anthropic; these are Anthropic's own measurements, on their datasets).

Retrieval can also be a tool. Instead of retrieving before every question, give the agent a search_manuals(query) tool, as in your loop. It then fetches "just in time", only when it decides it needs a page. Anthropic describes this approach as keeping lightweight references and loading data into context at runtime through tools (Anthropic engineering). It spends fewer tokens on questions that need no manual, such as "is the printer free?".

Notes and compaction 4 min

Suppose a long job, say rebuilding the booking schedule for a whole semester, fills the window before it is done. What then? Two techniques from Anthropic's engineering guidance apply (Anthropic engineering):

  • Compaction: when the context nears its limit, summarize the history and continue with the summary in place of the full text. Cost: details the summary leaves out are gone.
  • Structured note-taking: the agent writes notes to storage outside the context, such as a to-do list or "decisions so far", and reads them back later. This is memory the agent writes itself, with a tool such as save_note(text).

Compare this with section 3. Training status is written by your program from a trusted record. Notes are written by the model, so they can be wrong or stale. For anything with consequences, such as whether a student may use the laser cutter, read the authoritative record through a tool instead of trusting a note.

A common mix-up

"Summarizing the conversation is the same as remembering it." A summary is lossy: a student's exact booking time, dropped by the summary, cannot be recovered from it. Keep exact values in notes or a database, and let the summary carry only the gist.

Worked example and practice 5 min

Worked example

Place this fact: "The student passed the 3D printer safety course." Where should it live?

  1. Does it change between requests? No, it is stable, so it need not be recomputed each time.
  2. Must it survive past this session? Yes, the student returns later, so context alone cannot hold it.
  3. Is it trusted, consequential data? Yes, it decides whether a booking is allowed, so the program writes it to a database, not the model to a note.
  4. Is it searched by meaning in long text? No, it is a lookup by student id, so no index is needed.
  5. Decision: program-owned storage, read by a check_training_record tool and added to the context only when the question needs it.

Summary 2 min

  • The model sees only the context of the current call; it keeps nothing between calls, so the program re-sends everything.
  • History is re-sent at every step, so each token you add is paid for again on every later call; keep the fixed prompt and the tool results small.
  • Anything needed across sessions must be stored by your program and loaded back in.
  • Retrieval fetches only the few relevant chunks of a long document into the context.
  • Notes and compaction extend long tasks; notes can be stale, and summaries lose detail.
