The context window 5 min

You ask the assistant, "Is the laser cutter free on Friday?" and then follow up with "And Saturday?" How does the model know that "Saturday" still means the laser cutter? It does not remember the first question. It is shown it again.

The context window is all the text a model can look at when it writes a response, including the response itself. The Claude docs call it a "working memory" for the model (Claude docs: context windows). The model has nothing else to go on: no hidden state from the last call, no stored copy of earlier chats.

The window is measured in tokens, the small chunks of text a model reads and writes (a token is often a short word or part of a word). Two facts about tokens matter for you. The window has a maximum size, and you pay by the token. So whatever you put in the window costs money every time the model reads it.

What counts toward the window? More than the chat. The docs list the system prompt, every message, tool results, images, documents and your tool definitions (same page). The model's own output counts too.

Programmer's view: the context is the single argument to a stateless function, reply = model(context). Where the analogy stops: unlike a function argument, the input is not just data. It is also the instructions, and a long one makes the model's behavior depend on all of it.

What is kept between steps 6 min

Your agent loop makes several model calls for one request. If each call starts from nothing, how does step 3 know what step 1 found? Because the program sends it again. "Kept" in an agent means "resent".

In a typical agent, the program keeps a growing list of messages. Each step appends the model's output (a tool request or an answer) and the tool's result, then sends the whole list to the model. The docs put it directly: each message and response accumulates in the window, and earlier turns are preserved completely (Claude docs). In your own Python, this is a list you append to.

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # sends ALL of it
    messages.append(reply)                                # keep the model's output
    if reply is a final answer: break
    result = run_tool(reply)                              # the program runs it
    messages.append(result)                               # keep the result

The consequence is about money. Step 4 does not pay for only the new text; it pays to read steps 1 to 3 again. Total tokens read across a request grow much faster than the final context. You will compute this below.

A common mix-up

"A bigger context window makes the assistant remember more." It is tempting because "memory" and "window size" sound alike. But a window only sets how much text fits in one call. It saves nothing for next time, and filling it costs more per call. Anthropic also reports context rot: as the number of tokens grows, the model's ability to recall information from the context goes down, so more is not automatically better (Anthropic engineering; the context-window docs say the same).

When the window fills up 4 min

One manual search can return thousands of tokens, and the agent may search several times. What do you do when the list is too long, or too expensive? You shrink it on purpose. Anthropic's term for the whole job is context engineering: curating the set of tokens given to the model, with the goal of the smallest set of high-signal tokens (Anthropic engineering).

Two ways to shrink the context during a long task:

  • Clear old tool results. A manual page read three steps ago has usually done its job. The Anthropic post calls clearing tool results one of the safest, lightest forms of compaction.
  • Compaction. Summarize the conversation when it nears the limit, then start a new window with the summary. Claude Code keeps decisions and unresolved bugs and drops redundant tool output (same post). The risk: a summary can lose a detail you later need.
The Claude docs describe both as features the platform can do for you (server-side compaction, and context editing that clears tool results). You do not need to build them first; you need to know the assistant will need some policy.

Between sessions: notes as memory 5 min

The student finishes laser cutter training on Monday and opens a new chat on Thursday. The context from Monday is gone: a new session starts with a new, empty message list. How does the assistant know the student is trained? Only if something outside the context kept it.

That something is external memory: information the agent writes to storage and reads back later. The common form is notes. Anthropic describes structured note-taking as the agent regularly writing notes to memory outside the context window, such as a to-do list or a NOTES.md file, and pulling them back in later (Anthropic engineering). Your own tutor in this workspace does exactly this: NOTES.md is how it knows you between sessions.

The Claude memory tool is one implementation. Claude can create, read, update and delete files in a /memories directory that persist between sessions. It runs client-side: the model requests a file operation and your application performs it against storage you control (Claude docs: memory tool). That is the agent loop again, with a file as the tool. The docs also warn you to validate paths, cap file sizes and clear stale files.

A common mix-up

"The assistant automatically remembers earlier conversations." A chatbot product may do this for you, but a model called from code does not. Each session starts empty unless you build the saving and loading. This also decides what to store: Sam's training status is a fact to save as a record, while a chat transcript is rarely worth reloading whole.

Retrieval: finding the right page 5 min

The laser cutter manual is 200 pages. Pasting it into every call would cost thousands of tokens each time and bury the one relevant paragraph. What is the alternative? Keep the manual outside the context and bring in only the piece the question needs. That is retrieval.

Anthropic describes two timings. In pre-loaded retrieval, a search (often embedding-based) finds relevant chunks before the model runs, and they are placed in the context. In just-in-time retrieval, the agent holds lightweight pointers, such as file paths or stored queries, and loads data with tools at runtime. The trade-off is that runtime exploration is slower than retrieving pre-computed data. Claude Code is a hybrid: CLAUDE.md is loaded up front, while file search happens just in time (Anthropic engineering).

For you, the second form is your search_manuals tool from quiz 0001. The model asks, the program searches, and only the top matches come back as a tool result. Both forms share the point: the manual lives in storage, and the context holds a slice.

Worked example and practice 6 min

Worked example: the cost of one request

System prompt plus tool definitions: 1,550 tokens (this includes the student's question). Request: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The model asks for three tools in turn, then answers. Assume each model output adds 100 tokens, except the final answer. Tool results: calendar 300, manual search 2,000, training record 150. What is the total input read across the four calls?

  1. Call 1 reads 1,550. The model asks for the calendar (+100 output).
  2. Call 2 reads 1,550 + 100 + 300 = 1,950. The model asks for the manual search (+100).
  3. Call 3 reads 1,950 + 100 + 2,000 = 4,050. The model asks for the training record (+100).
  4. Call 4 reads 4,050 + 100 + 150 = 4,300, and the model writes the final answer.
  5. Total input: 1,550 + 1,950 + 4,050 + 4,300 = 11,850 tokens, against a final context of only about 4,300. The 2,000-token page is read twice.
Your turn

Same request, but the manual search returns 8,000 tokens instead of 2,000. Call 1 and call 2 are unchanged: 1,550 and 1,950. Work out the input of calls 3 and 4 and the total. Then name the one change from this lesson that would cut the most, and what it would do to call 4.

Show a solution

Call 3 reads 1,950 + 100 + 8,000 = 10,050. Call 4 reads 10,050 + 100 + 150 = 10,300. Total: 1,550 + 1,950 + 10,050 + 10,300 = 23,850 tokens. The page is now most of the bill. Returning only the best matching passage from the search tool, or clearing the page's result before call 4, would cut call 4 back to about 2,300.

Show a solution

Chat history: in the context, resent each call, trimmed by clearing old tool results. Training status: notes or a record the program saves and reloads at the start of a session, because it is per-student, changes and cannot be regenerated. Manuals: a searchable store reached by search_manuals, so only the matching passage enters the context.

Summary 2 min

  • The model sees only its context window; it keeps nothing between calls, and "kept between steps" means the program resends the whole message list.
  • Every call rereads the context, so total cost grows faster than the final context, and large tool results are paid for repeatedly.
  • When the context grows, clear old tool results or compact it into a summary.
  • Between sessions, only what the program stores survives: notes or records the agent writes and reloads.
  • Long documents stay in a searchable store; retrieval brings in just the slice a question needs.
