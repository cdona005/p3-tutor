Check your answer

Today's question is what "part of the next input" really means: what is in that input, how big it gets, and what survives once the loop ends.

The context window 5 min

When the assistant calls the model, what does the model actually see? Not a conversation it remembers, and not your booking system. It sees one block of text, and that block is everything it has to work with.

That block is the context: the text sent to the model in one call. For an agent it holds the system instructions, the tool descriptions, the message history so far, and every tool result so far (Anthropic, Effective context engineering).

Models read and write in tokens, which are chunks of text, often a short word or a piece of a longer one. The context window is the maximum number of tokens a model can take in one call, counting the input and what it writes back. Think of it as a fixed-size buffer: when the text does not fit, something must be cut.

Where the analogy stops: a buffer in your code holds bytes and never gets worse at reading them. A model reads everything in its window, and how well it uses that text can change with how much there is (next sections).

Why does size matter for you? Providers charge by the token for what goes in and what comes out, so a bigger context is a bigger bill on every call. Your budget limit is a token limit.

What is kept between steps 6 min

Your agent makes four model calls for one request. Does the model "remember" call 1 when it handles call 2? It does not. Each call is separate, and the program has to send the earlier steps again.

So the answer to "what is kept between steps" is: whatever the program puts back in. In the loop you traced, the program appends the model's tool request and then the tool result to the history, and sends the whole history in the next call. The history is the short-term memory.

In Python terms: the history is a list of messages you keep appending to, and every model call receives the whole list. If you forgot to append, the model would behave as if the step never happened.
Worked example: the cost of a four-call request

Assume the instructions, tool descriptions and question take 2,050 tokens, each tool request is about 100 tokens, and each tool result is about 1,500 tokens. These numbers are made up to show the pattern; measure your own.

  1. Call 1 sends 2,050 tokens.
  2. Call 2 sends those 2,050, plus a 100-token request and a 1,500-token result: 3,650.
  3. Call 3 adds another 1,600: 5,250. Call 4 adds 1,600 again: 6,850.
  4. Total input over the request: 2,050 + 3,650 + 5,250 + 6,850 = 17,800 tokens, though the final context is only 6,850.

The bill grows faster than the history, because old text is paid for again at every later step. Some providers discount a repeated, unchanged beginning of the input, but you still must keep the history short enough to fit and to stay useful.

A common mix-up (M8)

"The model remembers what it did earlier in the request." It is tempting because the agent seems to carry on one train of thought. But the model keeps nothing between calls; the program re-sends the history. If you trim a tool result from the history, the model has really lost it.

Check yourself

Show the answer

The third option. With the made-up numbers above, the input sizes climb in steps of about 1,600, so six calls cost much more than twice what three calls cost. Long agent loops are expensive for this reason.

A full window is not a good window 5 min

If a model's window is huge, why not paste in all the manuals and be done? Two problems: you pay for every token each call, and the model does not use all of that text equally well.

Anthropic describes models as having a limited attention budget: as the context fills, the model's ability to accurately recall information from it decreases, which they call context rot. Their rule for context design is to find the smallest set of high-signal tokens that gets the outcome you want (Anthropic).

Research on long inputs agrees. In a multi-document question-answering test, accuracy was highest when the relevant document was at the start or end of the input and dropped when it sat in the middle, even for models built for long contexts (Liu et al., Lost in the Middle).

A common mix-up (M7)

"If it fits in the window, the model will use it well." Fitting is not the same as being used. A 40,000-token manual that fits can still bury the one torque setting you need.

So an agent that runs many steps needs a policy for its history. Three standard ones, from the same Anthropic post:

  • Return less. Design tools to give back token-efficient results: a booking tool should return the free slots, not the whole calendar.
  • Compaction. When the history gets long, have the model summarise it and start a new context from the summary.
  • Sub-agents. A separate agent does a messy search in its own context and returns only a short result. Lesson later: when this pays off.

What is kept between sessions: notes 5 min

A student finishes laser-cutter training on Monday and comes back Thursday. Where does the assistant learn that? Not from the model: a new session starts a new, empty context, and the model carries nothing across.

What survives a session is whatever your program stored outside the model and loaded back in. That stored text is memory in an agent. Anthropic names a simple form of it, structured note-taking: the agent writes notes to storage outside the context and reads them back later (Anthropic).

For your assistant, a note can be a row in a database: {"student": "s1234", "laser_cutter_trained": true, "date": "2026-11-12"}. The program can read it at the start of a session, or give the model a tool get_training_record and let it look up when needed.

A common mix-up (M3)

"Memory is automatic: the assistant just remembers its past chats." Nothing is remembered unless you build it. Be careful what you save, too: a training status that matters for safety should live in a record your code controls, not in a chat summary the model wrote.

The third option. Save facts that stay true and will be needed later. Do not save what is already in the history, or what changes and can be looked up fresh.

Retrieval: finding the right page 5 min

The laser cutter manual runs to 120 pages and you have fifteen machines. You cannot put it all in the context, and you should not. How does the assistant find the one paragraph about focus height?

Retrieval means searching a collection outside the context and putting only the best matches into it. A common recipe: split each manual into chunks of a few hundred tokens, index them, and at question time find the chunks most similar to the question. Anthropic calls the model plus retrieval, tools and memory the basic building block of an agentic system (Building effective agents).

Anthropic also describes just-in-time retrieval: instead of loading everything up front, the agent keeps lightweight references, such as file paths or queries, and loads data into context with tools when needed (Anthropic). In your design, search_manuals(machine, query) is that tool.

Retrieval can miss. If the search returns the wrong chunk, the model answers from the wrong text or says it cannot find the answer. So retrieval quality, such as how you split the manuals and how the tool is described, is a design choice you test, not a given.

Check yourself

Why is retrieving three 500-token chunks usually better than placing a 40,000-token manual in the context?

Show the answer

The third option. About 1,500 tokens against 40,000, on every call that carries them, and the relevant text is easier for the model to use.

Worked example and practice 5 min

Worked example: sorting four facts

Request: "Is the laser cutter free Friday at 3, and what focus height should I use for 3 mm plywood?" Place each fact in the context, a saved note, or a retrieved manual.

  1. The question itself. Context. It exists only for this request and arrives in the history.
  2. Friday's free slots. A tool result, which joins the context for as long as it is needed. Do not save it: it changes, so look it up each time.
  3. The focus height for 3 mm plywood. Retrieval. It lives in a long manual, so search for the chunk and bring in only that.
  4. The student has completed training. A saved note. It outlives the session, and your code controls it.

The test for each: how long does it stay true, how big is it, and does the model need it on every call?

Your turn

Sort these three facts the same way, then say why: (a) the assistant's rule "never book a machine for a student without training"; (b) a student mentioned they prefer morning slots; (c) the 50-page 3D printer manual. Start with (a): it must apply on every call.

Show a solution

(a) System instructions, so it is in the context on every call. It is short and always needed. Enforce it in code as well, by checking the training record before booking.

(b) A saved note, because it stays true across sessions and is small. Load it at the start of a session.

(c) Retrieval. It is long, rarely all needed, and best searched on demand.

Summary 2 min

  • The context is the only thing the model sees in a call; the window caps its size and your bill grows with it.
  • Between steps, the program re-sends the history. Short-term memory is that list, and each step re-pays for it.
  • More context is not better context: keep the smallest set of high-signal tokens, and have tools return less.
  • Between sessions, only saved notes survive, and your program must write and load them.
  • Retrieval brings only the best-matching chunks of a long manual into the context.
