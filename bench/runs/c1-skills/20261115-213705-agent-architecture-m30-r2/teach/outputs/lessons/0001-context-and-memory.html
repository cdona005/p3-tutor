Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it lives in the context window, in saved notes, or in a searchable manual, and defend that choice with a token count.

Warm-up 2 min

Recall

From the agent loop: after the program runs a tool the model asked for, what does it do with the result, and is the next step part of the same model call or a new one?

Check your answer

The program puts the result into the model's next input and calls the model again, so each step is a separate model call. That second fact is today's starting point: if every step is a fresh call, something has to carry the earlier steps forward. That something is the context.

The context window 5 min

Problem: you ask a chatbot a question, and it can use your earlier message from a minute ago. Where does it keep that? Not inside itself. A model is a function from text to text, and between calls it holds nothing. Everything it can use has to be in the text you hand it on that call.

That text is the context window: all the text the model can reference when generating a response, including the response itself. The Claude documentation calls it the model's "working memory" (Claude docs, Context windows). If you think in code: it is the one argument to a pure function. Where the analogy stops: the argument has a hard size limit, and the function charges you by the size.

The size is counted in tokens, the chunks of text a model reads and writes (you met "one token at a time" in your first session on how a model works). A token is often a short word or part of a word, so a page of manual is roughly a few hundred to a thousand tokens. Treat any token figure in this lesson as a round number, not a measurement.

Everything in the request counts toward the window: the system prompt, every message, including tool results, and your tool definitions. The model's own output counts too (Claude docs).

A common mix-up (M3)

"The assistant remembers earlier conversations by itself." It is tempting because chat apps feel like they remember. They do so because the program stores the history and sends it again. The model has no memory of its own between calls, so anything you want it to know has to be put back into the context by your program.

What is kept between steps 6 min

Problem: in the agent loop the model makes several calls for one request. How does call 3 know what call 1 found? The program appends each tool request and each tool result to the message list, and sends the whole list each time. The Claude docs call this progressive token accumulation: each turn's input is all the previous history plus the new message (Claude docs).

That means what is "kept between steps" is exactly what your program keeps appending. It also means cost is not linear. The first call is small, but each later call re-reads everything before it, including that big manual page from step 2.

Add it up: 2,050 + 5,050 + 5,550 = 12,650 input tokens billed, even though the final context is only 5,550. Prompt caching can make repeated tokens cheaper, but the docs are explicit that it changes what you pay for those tokens, not whether they count toward the window (Claude docs).

When the context gets too full 5 min

Problem: if the list only grows, you hit the limit, and well before that you pay for dead weight. Going over the limit returns an error ("prompt is too long") or stops generation (Claude docs). There is a second, quieter problem: more context is not automatically better. Anthropic's engineers describe context rot: as the number of tokens grows, the model's ability to accurately recall information from the context decreases, so the goal is the smallest set of high-signal tokens (Anthropic, Effective context engineering for AI agents).

The program can trim the list. Two standard moves:

  • Tool result clearing: drop old raw tool outputs deep in the history. Anthropic calls it one of the safest, lightest forms of compaction, since once a tool has been called deep in the history the agent rarely needs the raw result again.
  • Compaction: summarize the conversation and start a new context window with the summary. The risk is that an over-aggressive summary drops detail that matters later, so start by keeping everything important, then cut.

Both are your program's choices, not the model's. In the Section 2 example, clearing the 3,000-token manual page once the answer is extracted would shrink every later call.

A common mix-up (M7)

"With a huge window we can paste everything in and skip this." Tempting because windows now reach up to a million tokens depending on the model. But you pay for every token on every call, and accuracy can fall as the context grows. A big window raises the ceiling; it does not remove the need to choose what goes in.

What is kept between sessions: notes 5 min

Problem: a student finishes laser-cutter training on Monday and returns on Thursday in a new session. A new session means a new, empty context. How does the assistant know?

It cannot, unless your program saves the fact outside the context window and loads it back. Anthropic calls this structured note-taking (agentic memory): the agent regularly writes notes to storage outside the context window, and pulls them back in later. Their examples are a to-do list or a NOTES.md file (Anthropic). In Python terms, it is a file or database row that your code reads at session start and writes at session end.

{"student": "s-4417",
 "trained": ["laser_cutter", "3d_printer"],
 "last_visit": "2026-11-12",
 "note": "prefers evening slots"}

Notice what is saved: a few facts, not the transcript. Replaying every old conversation would burn tokens on every call and invite context rot. Notes are a summary you chose.

Two design questions follow. Who writes the notes: the model through a tool such as save_note, or your program from authoritative data? For training status, a record in the university's own system is safer than the model's recollection. And what loads at the start: only that student's record, not everyone's.

Finding the right page: retrieval 6 min

Problem: the manuals total far more text than fits in a context window, and even if they fit you would not want to pay for them on every call. The assistant needs to fetch only the pages that matter. This is retrieval: search a store outside the context, and put only the best matches into it.

First, check whether you need it. Anthropic notes that if your knowledge base is smaller than 200,000 tokens (about 500 pages), you can include the whole thing in the prompt, and prompt caching makes that cheaper; beyond that you need a more scalable approach (Anthropic, Contextual Retrieval).

The common retrieval setup, called RAG (retrieval-augmented generation), has three preparation steps (Anthropic):

  1. Chunk the manuals into pieces, usually no more than a few hundred tokens.
  2. Embed each chunk: an embedding model turns it into a vector that encodes meaning.
  3. Store the vectors in a vector database, searchable by similarity.

At question time you embed the question, find the most similar chunks, and add them to the prompt. Think of it as a search index where "near" means "similar meaning", not "same characters".

That is also its weakness. Embeddings can miss exact matches. For a query like "Error code TS-999", keyword search (BM25) catches the exact string where embeddings may return general error-code text. Anthropic's hybrid approach runs both and merges the results (Anthropic). Your manuals are full of model numbers and error codes, so this matters.

A different pattern is just-in-time retrieval: give the agent tools to look things up (search, open a file section) and let it load only what it needs. It is slower than pre-computed retrieval and needs clear tool descriptions, but it fits changing content; Anthropic suggests doing the simplest thing that works (Anthropic).

A common mix-up (M8)

"Retrieval is the same as the model remembering." It is not: retrieval is your program searching a store and pasting results into the context. The model sees the pasted text like any other input, and if retrieval returns the wrong chunk, the model answers from the wrong chunk.

Choosing between the tools 4 min

Problem: you now have five moves (clearing, compaction, notes, retrieval, and a fresh context for a side task), and a design review will ask why you picked each. Match the move to the failure it fixes.

SymptomMoveCost to watch
Old tool outputs pile up inside one long requestClear tool resultsDeleting something a later step needs
One long conversation nears the limitCompaction (summarize, restart with the summary)A summary that drops a detail you needed
Facts must survive into the next sessionNotes saved outside the contextStale or wrong notes loaded as truth
The source text is far larger than the windowRetrieval of a few chunksRetrieving the wrong chunk
A side task would flood the main contextA sub-agent with a clean context that returns a short summaryExtra model calls and a summary that loses detail

Anthropic's guidance on the last row: specialised sub-agents handle focused tasks with clean context windows, and each may use tens of thousands of tokens or more but returns a condensed summary, often 1,000 to 2,000 tokens (Anthropic). You do not need that for the makerspace assistant yet. When it comes up in the multi-agent lesson, you will already know the reason for it: protecting the main context.

The same post says compaction suits long back-and-forth, note-taking suits iterative work with clear milestones, and multi-agent suits complex research where parallel work pays off. A makerspace chat is short, so for your first design the likely answer is: notes for the student's record, retrieval for the manuals, and clearing of old manual chunks. Compaction can wait until a session is long enough to need it.

The same rule applies to your budget: every token you do not send is a token you do not pay for. Trimming the context is a cost control as much as a quality control.

Worked example and practice 6 min

Worked example

The assistant gets: "Can I book the laser cutter Friday, and what settings for 3 mm acrylic?" Decide where each piece of information lives.

  1. Training status. Needed in every session, small, must be correct: a saved record loaded at session start (notes), preferably read from the authoritative system.
  2. Friday's calendar. Changes constantly and cannot be saved: a tool call at request time. The result enters the context for this request.
  3. Acrylic settings. The manuals are too big to include: retrieval, with keyword plus embedding search, and only the top few chunks enter the context.
  4. Old raw results. Once the settings line is extracted, clear the manual chunks so later calls do not pay for them again.
Your turn

Compute the input tokens billed for this run, round numbers, ignoring model output. The system prompt plus tools is 2,100 tokens and the question is 100. Four calls happen. After call 1 a 4,000-token manual result arrives; after call 2 a 1,000-token calendar result; after call 3 a 500-token booking confirmation. Step 1 is done for you: call 1 is 2,200 tokens. Now do calls 2 to 4 and the total, then redo calls 3 and 4 assuming the 4,000-token result was cleared after call 2.

Show a solution

Call 1: 2,200. Call 2: 2,200 + 4,000 = 6,200. Call 3: 6,200 + 1,000 = 7,200. Call 4: 7,200 + 500 = 7,700. Total 23,300. With the manual result cleared after call 2, call 3 is 7,200 - 4,000 = 3,200 and call 4 is 3,700, so the total is 2,200 + 6,200 + 3,200 + 3,700 = 15,300, saving 8,000 tokens. Clearing is only safe if nothing later needs that text.

Summary 2 min

  • The model keeps nothing between calls; the context window is everything it sees, and it is limited and billed.
  • Between steps, your program appends results and resends the whole list, so cost grows and old results should be cleared or summarized.
  • Between sessions, only what you save outside the context survives: small notes, loaded back at the start.
  • Retrieval searches a large store and puts only the best chunks in; use keyword plus embeddings for exact codes.
