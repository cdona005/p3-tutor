Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it lives in the context window, in saved notes, or in a searchable store, and defend the choice with a cost and a failure it avoids.

Objective O3: context and memory in an agent About 60 minutes Builds on: what a language model does, and the agent loop
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three are context-and-memory decisions. Your first design review will ask what the assistant keeps, what it saves and how it finds the right manual page; this lesson gives you the vocabulary and the numbers to answer.

Two questions from earlier sessions. Answer them in your head or on paper before you open the answers; recalling is what makes them stick.

Recall 1

The model has just asked for check_calendar("laser cutter", "Friday"). Who runs that function, and what happens to its result?

Check your answer

Your program runs it, not the model. The result is sent back to the model as input to its next call, and the loop repeats until the model writes a final answer or a limit stops it. Today's question is what, exactly, that "input to its next call" contains.

Recall 2

In one sentence: what does a language model do when you call it?

Check your answer

It takes text in and writes text out, one token at a time, from patterns learned in training. Notice what that sentence does not say: nothing in it stores anything. That fact drives most of this lesson.

The context window: everything the model can see 9 min

Suppose a student types "How do I change the blade?" and the assistant answers with a procedure for the wrong machine. Where did it get that? Not from a lookup. It produced text from whatever was in front of it. So the first question about any agent is: what, precisely, is in front of the model on a call?

The answer is the context: the set of tokens included when you sample from the model, per Anthropic's engineering team (Effective context engineering for AI agents). The context window is the limit on how much text the model can reference when generating a response, and the response itself counts toward it. Anthropic's documentation calls it a "working memory" for the model (Context windows, Claude docs).

A token is the unit the model reads and writes: a word, part of a word, or a piece of punctuation. A short English word is often one token; a long or unusual word, such as a part number, is split into several. You do not need an exact conversion. You need the habit of thinking in tokens, because tokens are what the window limits and what you are billed for.

What counts toward the window

More than the student's question. The docs say everything in the request counts: the system prompt, every message including tool results, images and documents, and your tool definitions. The output counts too. A prompt cache changes what you are billed, not what occupies the window (Claude docs).

If you have used Python, think of the context as the single list argument passed to one function call, and the model as a pure function of that list. There is no hidden global state. The analogy stops at one point: the function's output is not deterministic, so the same list can give different text.

What happens at the limit

If your input alone is larger than the window, the API rejects it with an error. On newer Claude models, if input plus the maximum output you allowed would exceed the window, the request is accepted and generation can stop early with a stop reason saying the window was exceeded (Claude docs). Chat apps such as claude.ai may instead drop the oldest content on a rolling basis. Your agent is not a chat app: your program decides what goes in, so your program has to handle the limit.

Show the answer

3,600 tokens. System prompt, tool definitions and question are all part of the request, and so is every token the model writes.

What is kept between steps 10 min

In the loop, the model asks for a tool, your program runs it and the model is called again. Does the second call "remember" the first? It does not, by itself. Each call is a separate request, and the model holds no state between calls. What makes the loop work is that your program builds the next request from the whole list so far.

Concretely, the agent's state between steps is one growing list of messages, which your program owns:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # a fresh request every time
    messages.append(reply)                               # keep what the model said
    if reply asks for a tool:
        result = run_tool(reply)
        messages.append(tool_result(result))             # keep what came back
    else:
        break                                            # final answer

This is the previous lesson's loop with the bookkeeping shown. The Claude docs describe the same accumulation: each user message and assistant response accumulates in the window, and previous turns are preserved completely (Claude docs). Preserved here means "included again in every request", not "stored inside the model".

A trace of the makerspace assistant

Here is what the list holds at each call for the request "Is the laser cutter free Friday at 3, and do I need training?" Read it top to bottom; each block is the full input of one model call, and the system prompt and tool definitions come before all of them.

Call 1 input:  [user] Is the laser cutter free Friday at 3, and do I need training?
Call 1 output: [assistant] tool request: check_calendar("laser cutter", "Friday")

Call 2 input:  [user] Is the laser cutter free ...
               [assistant] tool request: check_calendar(...)
               [tool result] Friday: 1-2 pm booked, 3-5 pm free
Call 2 output: [assistant] tool request: search_manuals("laser cutter", "training required")

Call 3 input:  everything in call 2's input and output, plus
               [tool result] chunk: "Operators must complete the 30-minute safety training ..."
Call 3 output: [assistant] "Yes, 3 pm Friday is free. You need the safety training first ..."

Three things to notice. First, the model's own tool requests are part of the list: without them, the tool result would arrive with no explanation of why it was asked for. Second, the original question is re-sent every time, which is how the model knows what it is working toward at call 3. Third, nothing in the trace is stored by the model; delete the list and the "memory" of this request is gone.

Why this is a cost problem

You are billed for the tokens in each request, so a result that arrives at step 1 is paid for again at steps 2, 3 and 4. A long tool result is not a one-time charge; it is a recurring one until it leaves the context. Prompt caching can lower the price of a repeated prefix, but the cached text still occupies the window (Claude docs).

Worked example: counting input tokens

The assistant has a 2,000-token base (system prompt, tools and question). It makes three tool calls, each returning 1,500 tokens. Each model reply that requests a tool is 60 tokens. These numbers are made up for practice; real counts vary. Total input tokens across the four model calls, ignoring caching?

  1. Call 1 input: the base only, 2,000.
  2. Call 2 input: base + reply 1 + result 1 = 2,000 + 60 + 1,500 = 3,560.
  3. Call 3 input: call 2's input + reply 2 + result 2 = 3,560 + 60 + 1,500 = 5,120.
  4. Call 4 input: 5,120 + 60 + 1,500 = 6,680. This call writes the final answer.
  5. Total: 2,000 + 3,560 + 5,120 + 6,680 = 17,360 input tokens. A naive estimate of 4 × 2,000 = 8,000 is off by more than half, because it ignores that earlier results are re-sent.

The total grows roughly with the square of the number of steps when each step adds a similar amount, which is why a loop that runs 20 steps costs far more than 5 loops of 4. This is the main reason the step limit from the previous lesson is also a budget control.

A common mix-up

"The model remembers the earlier steps, so I only need to send the new result." This is tempting because a chat feels continuous. The model has no memory between calls; if you send only the new result, it sees only the new result and cannot tell what question it is answering. Continuity is something your program rebuilds on every call.

Check yourself

In the loop above, a manual-search result of 4,000 tokens arrives at step 2 of a 6-step run. Roughly how many requests include those 4,000 tokens?

Show the answer

Four requests (calls 3, 4, 5 and 6), about 16,000 billed input tokens from one 4,000-token result, unless your program drops or shrinks it.

Why a full window is a problem, and what to do about it 10 min

Cost is one reason to keep the context small. If the window were large enough, would size be the only issue? No. The docs state that as token count grows, accuracy and recall degrade, a phenomenon called context rot, and that this makes curating what is in context as important as how much space there is (Claude docs). The Anthropic engineering post explains it as an "attention budget": the model draws on a finite budget when reading a large context, so context is a finite resource with diminishing returns. Its goal is the smallest possible set of high-signal tokens that gets the outcome you want (Anthropic).

For you, that means a 300-page manual pasted into every call is bad twice: it is expensive on every step, and it can make the model worse at finding the one paragraph that matters.

Three ways to shrink what rides along

  • Clear old tool results. Once the model has used a result, replace it with a short stub such as "manual search result removed". The engineering post calls this one of the safest, lightest-touch forms of compaction.
  • Compact. When the context nears the limit, have the model summarize the conversation and start a new context with the summary. In Claude Code, per the post, the summary keeps architectural decisions, unresolved bugs and implementation details and drops redundant tool output. Cost: a summary can drop a detail you later need.
  • Use a sub-agent with its own context. A sub-agent may use tens of thousands of tokens exploring and return only a condensed summary, often 1,000 to 2,000 tokens. You will compare this with a single agent in a later lesson; for now, note that it is another way to keep a main context small.

The docs also list server-side compaction and context editing (tool-result clearing) as features of the platform for long-running agents. Whether you use the platform's feature or write the few lines yourself, the design question is the same: what does the model still need at the next step?

What a compaction summary must keep

Suppose the assistant is helping a student plan a three-part project and the context is nearly full. A summary that says "the student wants to build a box" is short and useless. A useful one keeps what the next step depends on:

  • Decisions made: "Box is 3 mm plywood, laser cut, finger joints."
  • Open items: "Needs a booking; student has not yet confirmed Friday."
  • Facts the model must not re-guess: "Training record checked: valid."
  • Pointers instead of bulk: "Manual section 4.2 was retrieved; search again if needed", not the section text.

The test for any item is whether a fresh model call, seeing only the summary, could take the next step correctly. This is the same question as the one for clearing tool results: what does the model still need?

TechniqueWhat it removesRisk
Clear tool resultsRaw output the model has already usedModel must re-fetch if it needs it again
CompactionMost of the conversation, replaced by a summaryA needed detail is lost in the summary
Sub-agentThe exploration work, kept in a separate contextMore model calls and complexity

What is kept between sessions: nothing, unless you save it 8 min

A student trains on the laser cutter on Tuesday. On Thursday they open the assistant and ask "Can I book it?" The model was not there on Tuesday. When Tuesday's conversation ended, its context was thrown away: a new session starts with an empty list. So where does the answer come from?

Only from your program. The model's weights do not change when it talks to a user. A session is one run of the assistant from first message to the end of the conversation. Memory, in an agent, means information stored outside the context window and put back into it later. It exists only if you build it.

Compare HTTP. A web server handles each request with no memory of the last one, and anything that "remembers" you does it with a database or a session store that the server reads. An agent is the same: stateless calls, with state kept in your storage.

A save-and-load sketch

In Python terms, a first version needs two functions and one file. The sketch is deliberately plain so you can see there is no magic in it:

import json, datetime

def load_student_notes(student_id):
    try:
        with open(f"notes/{student_id}.json") as f:
            return json.load(f)              # a short list of dated lines
    except FileNotFoundError:
        return []

def save_student_note(student_id, line):
    notes = load_student_notes(student_id)
    notes.append({"date": str(datetime.date.today()), "note": line})
    with open(f"notes/{student_id}.json", "w") as f:
        json.dump(notes[-20:], f)            # keep only the last 20 lines

# at session start, before the first model call:
notes = load_student_notes(student_id)
system_prompt = BASE_PROMPT + "\nNotes about this student:\n" + format(notes)

Each design choice here answers a cost or failure question. The note list is capped at 20 lines so loading it cannot grow without limit. Every note carries a date so the model, and you, can tell old from new. The notes go into the system prompt once per session, not into every tool result. The training status is not stored here at all: it stays in the training system and is read through a tool, so it cannot go stale in a note.

One more point for your review: the model does not need to be the one that saves. Your program can write a note when a booking succeeds, with no model call and no model cost. Use the model to write a note only when judgment is needed, such as summarizing what a student was struggling with.

Two kinds of thing to remember

  • Facts with an owner and an authority: "Dana completed laser cutter training on Tuesday". This is a database record, written by the training system, read by a tool such as check_training_record. The model should not be the source of truth for it, and you should not leave it to the model to remember to save it.
  • Notes the agent writes for itself: "Dana prefers evening slots; asked about the 3D printer twice". This is softer and can be written by the agent or by your program.

Either way the loop is the same: save when something happens, load at the start of a session, put the loaded text into the context. Load only what this request needs, because everything you load costs tokens on every step.

A common mix-up

"A good enough assistant remembers its users." It is tempting because products like chat apps do seem to remember. When they do, it is a feature built around the model: stored text that is loaded back in. A bare model call, which is what you get when you write the loop yourself, remembers nothing. Neither a bigger window nor a stronger model changes this; the window only holds what you load into it during one session.

Retrieval: finding the right manual page 12 min

The laser cutter manual runs to 200 pages, and a student asks what to do when the exhaust fan alarm sounds. Pasting the whole manual into every call fails on cost and on context rot. Giving the model nothing fails because it will answer from general training, and you have already seen that it can state outdated facts with confidence. What is the middle path?

Retrieval means fetching only the few passages relevant to the current question and putting those in the context. The setup has two parts, one done ahead of time and one per question.

Before any question: prepare the store

  1. Split each manual into chunks: passages of a few hundred tokens, ideally cut along headings or procedure steps so each chunk makes sense alone.
  2. Index the chunks so you can search them (next section).
  3. Keep metadata with each chunk: machine name, manual title, page or section. This lets the model cite its source and lets you filter by machine.

Per question: search, then answer

Two search methods are common, and they fail in opposite ways:

MethodHow it matchesStrengthWeakness
Keyword search (such as BM25)Shared words, with rare words counting moreExact terms: part numbers, error codes, "E-04"Misses paraphrase: "fan alarm" vs "exhaust fault"
Embedding searchEach chunk and the question become vectors; nearest vectors winMeaning, even with different wordsCan miss exact identifiers

An embedding is a list of numbers produced by a model so that texts with similar meaning get similar lists. You do not need the math (it is out of scope for your mission); you need to know that "nearest vector" means "most similar meaning". Anthropic's retrieval write-up describes combining both methods, and also describes adding short context to each chunk before indexing, because a chunk like "Replace it every 500 hours" loses what "it" is when cut from the page (Contextual Retrieval, Anthropic). For a makerspace you can get the same benefit cheaply by prefixing each chunk with its machine name and section title.

What a good chunk looks like

Chunking is where many first retrieval systems quietly fail, so look at one case. A manual page reads: "4.2 Changing the blade. Switch off and unplug the saw. Loosen the two side screws. Slide the old blade out. 4.3 Blade tension. Set the tension dial to 3 for blades under 6 mm." Compare two ways to cut it.

  • Fixed 20-word cuts: one chunk ends with "Slide the old" and the next begins "blade out. 4.3 Blade tension". A search for "how do I change the blade" may return the first half of the procedure, and the model will invent the rest or answer wrongly.
  • Cuts at section boundaries, with a prefix: "Band saw, section 4.2, Changing the blade: Switch off and unplug the saw ..." The whole procedure is in one chunk, and the prefix says which machine it belongs to.

The second version costs a little more care when you prepare the manuals and nothing at question time. If the manuals are long, set a size limit and split a section only at a step boundary. Keep a short overlap, such as repeating the section title, so a chunk is never an orphan.

Two more numbers to decide. How many chunks to return: more chunks improve the chance the answer is present but cost tokens on every later call; start with three to five and measure. How to check it works: write twenty real student questions with the manual section that answers each, run the search, and count how often the right section is in the results. That count is a measurement you can show at a design review, and it tells you whether to improve the chunks, the search method or the model.

Retrieval as a tool, and when to load

Notice that the bottom row is a tool call: search_manuals(machine, query). The agent decides when to search, can rephrase and search again if the first results do not answer the question, and gets back a small result. Anthropic's post contrasts this just-in-time approach, where the agent keeps lightweight identifiers such as file paths or stored queries and loads data with tools at runtime, with loading everything up front. Its Claude Code example puts CLAUDE.md files in context up front, while glob and grep fetch files just-in-time, and it recommends a hybrid. Runtime exploration is slower, but it keeps the context lean (Anthropic).

For your assistant, a hybrid is natural: put the short, always-relevant facts (makerspace hours, the list of machines) in the system prompt, and retrieve everything bulky (manual pages) on demand. Put it as a rule: anything the assistant needs on nearly every request is a candidate for the prompt; anything it needs on some requests is a candidate for retrieval.

A common mix-up

"Retrieval means the model reads the manual." The model never touches the manual files. A search tool, written by you, returns text, and your program puts that text into the context. If the right chunk is not returned, the model cannot use it, so most retrieval failures are search failures, not model failures. When an answer is wrong, check what the search returned before you change the prompt.

Notes as memory 7 min

Retrieval fetches from material that already exists. What about an agent that works for a long time, such as one helping a student plan a multi-part project over many steps, and whose context fills up and is compacted or reset? How does it keep track of its plan?

Structured note-taking (also called agentic memory) is the answer in Anthropic's post: the agent regularly writes notes to storage outside the context window, and those notes are pulled back into context later. The post's examples are Claude Code's to-do lists and a custom agent keeping a NOTES.md. In its Claude-playing-Pokemon example, the agent keeps tallies, objectives, maps and strategy notes, and after a context reset it reads them and continues (Anthropic).

That description also fits the folder you are learning in: NOTES.md is a note file that your tutor reads at the start of each session. The mechanism is just files, which is why it is easy for a student team to build.

Design questions for any memory

  • What is worth saving? Decisions, current status, preferences, open items. Not raw tool output or whole transcripts.
  • Who writes it? The agent through a save_note tool, or your program at the end of a session. A program-written record is more predictable; an agent-written note is more flexible and can be wrong.
  • How does it get back in? Load a short summary at session start, or let the agent call a read_notes tool. Loading all notes grows the context every session; reading on demand keeps it small.
  • How does it go stale? Notes record what was true when written. A training status that expired last month must not be trusted blindly; store a date and check authoritative records for anything that matters.
  • Privacy. Notes about students are personal data. Save the least that makes the assistant useful.
The Claude platform also offers a memory tool and the engineering post mentions a file-based one in beta. You can build the same thing with two functions and a JSON file, which is a reasonable first version for a design project.

Worked example and practice: the makerspace assistant 12 min

Worked example: a placement decision

For each item, choose where it lives: prompt (always in context), retrieval (fetched when needed), record (database read by a tool) or note (saved by the agent or program).

  1. "The makerspace is open 9 to 9 on weekdays." Short, needed on many requests, changes rarely: prompt. Cost: a few dozen tokens on every call, and you must edit the prompt when hours change.
  2. The 3D printer manual. Bulky and needed on some requests only: retrieval, chunked by section with the machine name on each chunk.
  3. "Dana completed laser cutter training on 4 March." A fact with an authority and a consequence if wrong: record, read by check_training_record. Do not rely on a note for a safety question.
  4. "Dana prefers evening slots." Soft, helpful, harmless if stale: note, dated, loaded at session start as one line.
  5. The booking calendar. Changes constantly and is the source of truth for the booking: record via check_calendar, fetched live and not saved in notes.

Next, the cost for a request that uses retrieval. Base 2,000 tokens. The assistant calls search_manuals (reply 60 tokens, result 1,200 tokens for three 400-token chunks), then answers. Call 1 input is 2,000; call 2 input is 2,000 + 60 + 1,200 = 3,260; total 5,260. Had it put the 20,000-token manual in the result instead: 2,000 + 22,060 = 24,060 for the same two calls. Retrieval is about 4.6 times cheaper here, and every added step widens the gap.

Show a solution

(1) Prompt: short and needed to route almost every request. (3) Record: an authority with consequences, read live via a tool. (4) Retrieval: bulky and needed only for laser cutter questions, chunked and indexed.

Your turn: cost with steps faded

Same base of 2,000 tokens and 60-token tool-request replies. The run has three model calls: call 1 requests search_manuals; call 2 requests check_training_record; call 3 writes the answer. The search result has X tokens and the training record result has 100 tokens. Write the total input tokens as a formula in X, then evaluate it for X = 20,000 (whole manual) and X = 1,200 (three chunks). Start with call 1 = 2,000.

Show a solution

Call 1: 2,000. Call 2: 2,000 + 60 + X = 2,060 + X. Call 3: call 2's input + 60 + 100 = 2,220 + X. Total: 6,280 + 2X. For X = 20,000: 46,280. For X = 1,200: 8,680. The manual result is carried through two later calls, which is why its size is counted twice (the 2X).

Your turn: argue it

A teammate says: "We should use a model with a huge window and put all the manuals in the prompt; then we need no retrieval." Write three bullets for the design review that answer them using this lesson.

Show a sample answer
  • Cost: the prompt is re-sent on every call of every request, so we pay for the full manuals many times per question.
  • Quality: accuracy and recall degrade as the context grows, so more text can mean worse answers, even when it fits.
  • Maintenance: manuals change, and with retrieval we re-index one document instead of rewriting the prompt. A concession worth making: for a very small manual set, putting everything in the prompt can be a fair first version.

Summary 3 min

  • The model sees only the context: system prompt, tool definitions, messages and tool results, all counted against the window and your bill.
  • Between steps, your program re-sends the whole list; nothing is kept inside the model. Early results are paid for again on every later call, so total cost grows faster than the step count.
  • A bigger window does not remove the need to curate: context rot makes recall worse as it fills. Clear used tool results, compact, or delegate.
  • Between sessions nothing survives unless you save it and load it back. Facts with consequences belong in records; soft preferences in short dated notes.
  • Retrieval puts a few relevant chunks in context through a search tool; use keywords for exact terms, embeddings for meaning, and debug the search before the prompt.

Say it in your own words: without looking, explain to a teammate why the assistant "knows" Dana trained on Tuesday, and where that fact lives when no session is running.
