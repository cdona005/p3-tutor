Context and memory in an agent

By the end of this lesson you can write a one-page memory plan for the makerspace assistant: what stays in its context, what it saves between sessions, and how it finds the right page in a long manual.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 60 minutes
Why this matters for you

Your design review will ask three things: why the assistant does not forget a student's training status, how it answers from hundreds of manual pages, and what that costs per request. All three are context and memory decisions, and you are the one defending them.

Warm-up 4 min

Two questions from earlier sessions. Answer from memory before you open the reveal; retrieving it is the point.

Recall 1

In the agent loop, the model asks for a tool. Who actually runs the tool, and what happens to the result?

Check your answer

The program around the model runs the tool, not the model. The result is added to the conversation and the model is called again. Each step of the loop is a separate model call. Today's lesson is about what that second call actually contains.

Recall 2

A language model writes its output one token at a time. What is it given to produce each token?

Check your answer

Text in, text out: it is given the text so far and picks the next token from patterns learned in training. "The text so far" is exactly what we call the context, and the next hour is about who decides what goes into it.

The context window: what the model can see 9 min

A student asks the assistant, "Can I use the laser cutter tomorrow?" The model answers well. A minute later the same student asks, "And the day after?" Does the model know "it" means the laser cutter? Only if the first question is in front of it again. The model has no hidden mind holding the conversation; it has only the text it is handed on each call.

That handed-over text has a name. Context is the set of tokens included when sampling from a language model (Anthropic, "Effective context engineering for AI agents"). A token is a chunk of text, often a word or part of a word; the model reads and writes in tokens, and so does the bill. The context window is the maximum number of tokens the model can take in and produce in one call.

If you know programming, treat the context as the argument list of a pure function: answer = model(context). The function keeps no state between calls. Where the analogy stops: unlike a function argument, the context is not just stored, it is read by attention, and more of it is not free, as you will see below.

What is in the context

In your assistant, everything the model reads in one call sits in one place:

  • System prompt: the assistant's role and rules.
  • Tool definitions: the name and description of check_calendar, search_manuals and the rest. The model cannot see your tool code, only these descriptions, so they cost tokens on every call.
  • The conversation so far: the student's messages, the model's earlier replies, its tool requests, and the tool results.
  • Anything else you inject: a student's saved profile, retrieved manual pages.
Window sizes change with model versions and are listed in the provider's documentation. Design against the limit you have, and treat the number as something to look up, not memorize.
A common mix-up

"A bigger context window means the model uses all of it equally well." It is tempting because "fits" sounds like "understood". Anthropic reports the opposite pattern, called context rot: as the number of tokens grows, the model's ability to accurately recall information from the context decreases (same source). The post describes an "attention budget" that every new token draws down. Fitting is necessary; it is not sufficient.

Check yourself

You add a 40-page laser cutter manual to the system prompt "just in case". The whole thing fits in the window. What is the best description of the effect?

Show the answer

The third option. Context is paid for and read on every call, and irrelevant text competes for the model's attention. The model learns nothing permanent from it.

Between steps: the transcript is re-sent 10 min

The agent loop has three tool calls in a row. How does the third model call know what the first two returned, if the model keeps no state? Because your program hands it all of it again. What persists between steps is not in the model; it is a list your program keeps and re-sends.

Sketch of the loop's state in Python:

messages = [{"role": "user", "content": "Is the laser cutter free tomorrow, and do I need training?"}]

while True:
    reply = call_model(system_prompt, tools, messages)   # the whole list goes in
    messages.append(reply)                               # the model's turn is kept
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)                # your code runs the tool
    messages.append(tool_result(result))                 # the result is kept too

The list messages is the working memory of the agent: short-term, per task, and held by your program. It is what the Anthropic memory tool docs refer to when they say Claude requests file operations and the application runs them and returns a tool_result (memory tool docs): the loop's structure is the same, and the result lands in the same list.

Why this drives your cost

Each call re-sends the system prompt, the tool descriptions and every earlier message. So the input grows each step, and the total tokens processed across a run grow faster than the number of steps. A tool that returns a 3,000-token manual chapter at step 2 is paid for again at step 3, step 4, and every step after, unless you remove it.

StepNew tokens addedTokens sent in this call
1: question200 (prompt + tools) + 30230
2: calendar result300530
3: manual search result3,0003,530
4: final answer call2003,730

The task itself is small: a few thousand tokens. But the sum of the "sent" column is about 8,000 tokens, because early content is paid for again on each later call. (The numbers are illustrative; the shape is what to remember. Providers also offer caching of repeated prefixes, which reduces the price of re-sent text, but it does not remove the growth. Check the current pricing page before you budget.)

So cost per request is shaped by three things you control: the size of tool results, the number of steps, and what you drop from the list between steps. That is a design choice, not a model setting.

A common mix-up

"The model remembers what the tool returned earlier, so I don't pay for it again." It does not remember anything: every call is a fresh read of the list your program sends. If the old result is still in messages, it is sent and billed again; if you removed it, the model cannot see it at all.

Check yourself

Your assistant runs 6 steps. Step 2 returns a very large search result that is never needed again. Which change cuts cost most?

Show the answer

The first option. The cost is in tokens re-sent each call, so remove the big, finished result. A larger window changes the limit, not the bill.

When the context fills up 9 min

A long conversation with a student, 60 turns of questions about three machines. At some point the list reaches the window limit, or long before that it gets expensive and the model starts missing things. What do you cut, and how do you avoid cutting what matters?

Anthropic frames the goal as finding the smallest set of high-signal tokens that gives the desired outcome, since context is a finite resource with diminishing returns (Anthropic). Three techniques recur, from lightest to heaviest:

  1. Clearing old tool results. Once the model has used a raw result, replace it with nothing or a one-line stub. The post calls this "one of the safest lightest touch forms of compaction".
  2. Compaction. Summarize the conversation so far and start a new context with the summary. In Claude Code the model preserves architectural decisions, unresolved bugs and implementation details and drops redundant tool output. The post warns that overly aggressive compaction can lose context that turns out to matter later.
  3. Sub-agents. Hand a sub-task to a separate agent with a clean context; it returns only a condensed summary, often 1,000 to 2,000 tokens. You will meet this properly in the multi-agent lesson, so treat it as a preview here.
TechniqueSavesRisk
Clear old tool resultsLarge, finished outputsThe model needs the raw text again and must re-call the tool
CompactionWhole conversation historyThe summary drops a detail you needed later
Sub-agentA whole sub-task's workExtra calls and complexity, and summary loss
For the makerspace assistant, most conversations are short: a student asks two or three things. You may need none of the three at first. The post's own closing advice is to do the simplest thing that works.
Check yourself

A student chats for an hour about a 3D printer. Early on they said their filament is PETG and that they are in the evening training group. After compaction, the summary omits both. What went wrong?

Show the answer

The third option. A summary keeps what the summarizer judges important. Facts that must never be lost belong in a durable place outside the conversation, which is the next section.

Between sessions: notes as memory 10 min

A student finishes laser cutter training on Monday and returns on Thursday to book it. The conversation from Monday is gone: a new session starts with an empty list. How does the assistant know the student is trained?

It cannot, unless something outside the context persisted. Between sessions the model keeps nothing, and your messages list is discarded when the session ends. So long-term memory means information written to storage you control, and read back into context when needed. The storage can be a database row, a JSON file, a text file.

Anthropic describes this as structured note-taking, or agentic memory: the agent regularly writes notes persisted outside the context window, and those notes are pulled back in at later times. The post's example is Claude playing Pokémon, which keeps tallies and maps of explored regions, then reads its own notes after a context reset and continues (Anthropic). In Python terms: a notes file is a persistent dict, and the context is the local variables that vanish when the function returns.

The memory tool, as a concrete design

Anthropic's memory tool is a file-based version of this. It "operates client-side: Claude requests file operations, and your application runs them." The model can view, create, str_replace, insert, delete and rename files under a /memories path, and your handler maps that path to real storage, such as a per-user directory or database keys. When enabled, Claude checks its memory directory before starting a task (memory tool docs).

Notice what this is: the memory is just one more tool, in the same loop you already know. The model asks, your program does it, the result returns. Persistence is only as durable as the storage you implement, and your handler must block paths that escape /memories. You do not have to use this particular tool; you can implement the same idea yourself with a fixed lookup.

Two designs for the makerspace

Fixed lookupModel-written notes
HowProgram loads the student's row (trained machines, dates) into the context at session startThe model decides what to save and read through a memory tool
Best forFacts with a known shape, like training statusOpen-ended facts, like preferences or past problems
Cost and riskPredictable tokens; cannot save what you did not plan forExtra calls; the model may save wrong or stale facts

For training status, the fixed lookup is the safer design: the source of truth is your training database, not what the model wrote down. A model-written note saying "trained on the laser cutter" could be wrong, and a booking decision should not rest on it.

A common mix-up

"Long-term memory means the model learns from our conversations." It is tempting because chat products feel like they remember you. But using the model does not change it; the model's training is fixed. Memory is text your system saves and puts back into the context. If it is not in the context on a call, the model cannot use it.

Check yourself

Which statement about the Thursday booking is correct?

Show the answer

The third option. Between sessions, persistence comes only from storage you control, read back into the context.

Retrieval: finding the right manual page 11 min

The laser cutter manual is 300 pages and the assistant has five machines. A student asks, "What power setting for 3 mm acrylic?" You cannot send all the manuals each call (Section 2 showed why). How does the right half page get into the context?

Retrieval is selecting a small part of a large body of text and putting only that part in the context. Retrieval is memory in the sense that matters here: a store of knowledge too big for the context, with a way to pull the relevant piece in. Anthropic names two timings (Anthropic):

  • Up front: before the model is called, your program searches (the post describes embedding-based retrieval as the common form) and puts the top results into the context.
  • Just in time: the agent keeps lightweight references, such as file paths or stored queries, and loads data at runtime using tools. In your assistant, that is search_manuals(query) as a tool the model chooses to call.

The post notes the trade-off: runtime exploration is slower than retrieving pre-computed data, and it suggests a hybrid, with some data up front for speed and more exploration at the agent's discretion. Claude Code is its example: it drops CLAUDE.md into context up front, while search tools like glob and grep retrieve files just in time.

How a search tool finds pages

Two common ways, and you can combine them:

  • Keyword search: match words, like grep. Fast and exact; it misses a page that says "engraving depth" when the student wrote "how deep to burn".
  • Embedding search: convert each chunk of text to a list of numbers so that chunks with similar meaning are close together, and find the chunks nearest the question. It handles different wording; it can return something plausible but wrong, so the chunk's source should travel with it.

Both start with chunking: split each manual into pieces, such as a section at a time, with a title and page number on each. Chunks too large waste context; chunks too small lose the surrounding conditions, such as "for acrylic only".

A common mix-up

"If the search returns the right chunk, the model will answer correctly." It is tempting because retrieval looks like the hard part. But if the search misses, the model never sees the right page, and may still answer confidently from training patterns, the outdated-fact problem you have already noticed in chatbots. Have the assistant cite the page it used, and say "not found" when the search returns nothing relevant.

Check yourself

A student asks "how deep can I burn into plywood?" The manual says "maximum engraving depth for plywood". Keyword search returns nothing. What is the most likely fix?

Show the answer

The third option. The failure is in the search, so fix the search: match by meaning, or let the model retry with a reworded query.

Choosing where each fact lives 10 min

You now have four places a fact can live. Someone at the design review asks, "Why is the training record loaded at the start instead of searched for?" You need a rule, not a feeling. Here is one that works for most assistants, and the questions behind it.

PlaceLives how longWho controls itUse for
Always in contextEvery callYou, in codeRules, tool descriptions: small and needed every time
Message listOne sessionYour loopWhat happened in this task: questions, tool results
Stored record, loaded at startAcross sessionsYour databaseFacts with a known shape that must be right
Searchable storeAcross sessionsYour indexBig bodies of text: manuals, policies

Ask four questions about each fact, in order:

  1. Is it needed on almost every call? If yes and it is small, put it in the always-present context. If it is large, you cannot afford it every call, so go on.
  2. Must it be exactly right? If a wrong value causes a wrong action, such as a booking for an untrained student, keep it in a database you control and load it, rather than relying on text the model wrote.
  3. Is it too big to load whole? If yes, make it searchable and retrieve a few chunks per question.
  4. Does it need to survive the session? If yes, write it outside the context. If not, leave it in the message list and clear it when finished.

This is the same habit as choosing a data structure: a constant, a row in a table, a file on disk and a local variable all hold data, and the question is how long, how big and how exact. The analogy stops at one point: a local variable is free to keep, but every token in the context is paid for again on every call.

A cost estimate you can defend

Your sponsor's budget is small, so the review will want a number. You can produce a rough one with three inputs: tokens sent per call, calls per request, and the price per token. Using the pattern from Section 2:

fixed per call   = system prompt + tool descriptions   (say 1,200 tokens)
steps            = 4 calls per request
tool results     = 300 (calendar) + 800 (manual chunks)
call 1 sends     = 1,200 + 30
call 2 sends     = 1,230 + 300
call 3 sends     = 1,530 + 800
call 4 sends     = 2,330 + 150  (small final-answer turn)
total tokens sent = 1,230 + 1,530 + 2,330 + 2,480 = 7,570 tokens

Notice what dominates: the fixed 1,200 tokens are sent four times, which is 4,800 of the 7,570. Shrinking the tool descriptions saves more than shrinking the manual chunks here. You cannot see that without doing the sum, and a team guessing from intuition would target the wrong thing. Multiply the total by your provider's current input price per token (look it up on its pricing page; prices change) and by requests per month to get a budget line.

Output tokens are usually priced differently from input tokens, and caching can lower the price of the repeated fixed prefix. Both change the number, not the method.
A common mix-up

"Retrieval and memory are the same thing, so one vector store handles everything." They overlap, but they serve different needs. A manual is large, public and rarely changes, so search suits it. A student's training status is small, private and must be exact, so a database lookup suits it. Putting training status in a similarity search can return the wrong student's record or a stale one, because similar text is not the same as the right row.

Check yourself

The assistant should apologize in a friendly tone and never reveal other students' bookings. Where do these two rules live?

Show the answer

The second option. Rules that must hold on every call go in the always-present context, and the privacy rule should additionally be enforced by the program, for example by only letting the calendar tool return the current student's own bookings.

Worked example and practice 12 min

Worked example

A student, Jo, starts a session: "Book me the laser cutter Friday at 3, and what's the max power for acrylic?" Plan what goes where.

  1. Always in context (every call): system prompt and the three tool descriptions. These are small and the model cannot work without them.
  2. Loaded at session start (fixed lookup): Jo's training record, one line: "Laser cutter: trained 2026-10-02." Small, exact, and from the database, so it is trusted. Reason: the booking rule depends on it.
  3. Retrieved just in time: search_manuals("laser cutter acrylic max power") returns three chunks with page numbers. Only now does manual text enter the context. Reason: it is relevant to this one question.
  4. Dropped after use: once the answer is written, the raw calendar result and the two unused chunks are cleared from the list in case the session continues. Reason: they are paid for on every later call.
  5. Saved between sessions: the booking itself goes in the booking system (not a note); a model-written note such as "Jo prefers afternoons" goes to a small notes file. Reason: the booking is a fact for the system of record, the preference is soft.
Your turn

Same assistant, new case. Sam asks: "Last week you told me the 3D printer bed needed re-leveling. Did I ever fix that? Also, what's the nozzle temperature for PLA?" Using the five buckets above, decide what goes in each. The first bucket is done: always in context: system prompt and tool descriptions. Do the other four before you open the solution.

Show a solution

Loaded at start: Sam's profile and any saved notes, which is where "needed re-leveling" would have been recorded. Without it, the assistant has no basis for "last week". Retrieved just in time: the PLA nozzle temperature from the 3D printer manual, with page citation. Dropped after use: the manual chunks that did not contain the temperature, and any large tool results. Saved between sessions: an update to Sam's notes if Sam says it was fixed, and this time the note should say who said so and when, because the model cannot verify it. If no note about re-leveling exists, the correct answer to the first question is "I have no record", not a guess.

Draft your memory plan 5 min

This is the win from the top of the page. Open a blank page and write the plan for your own assistant, using the template below. Do it before you read the sample; writing it yourself is the retrieval practice that makes it stick.

ALWAYS IN CONTEXT:        (what, roughly how many tokens)
LOADED AT SESSION START:  (which stored records, from where)
RETRIEVED JUST IN TIME:   (which store, how it is searched, how many chunks)
CLEARED AFTER USE:        (which tool results, and when)
SAVED BETWEEN SESSIONS:   (what, where, written by whom)
FAILURE CHECK:            (what happens if the search finds nothing,
                           or a stored fact is missing)
Show a sample plan

Always: system prompt with privacy and tone rules, plus three tool descriptions, about 1,200 tokens. At start: the student's training record from the training database, about 50 tokens. Just in time: search_manuals over chunked manuals, keyword plus embedding search, top 3 chunks, each with machine name and page. Cleared: calendar results and unused chunks, after the answer is written. Saved: bookings in the booking system, written by the booking tool; soft preferences in a short per-student notes file, written by the model and capped in size. Failure check: if search returns nothing relevant, the assistant says it could not find it and points to the staff; if the training record is missing, it treats the student as untrained and says so, rather than guessing.

Your plan will differ, and the review will push on the failure check most. A plan that says what the assistant does when memory is wrong is stronger than one that only describes the happy path.

Summary 3 min

  • The model keeps no state. Its context, the tokens it is given each call, is everything it can use, and the context window caps its size.
  • Between steps, your program keeps the message list and re-sends it every call, so cost grows with each large result you leave in.
  • Long contexts degrade recall (context rot), so shrink them: clear old tool results, compact, or hand off to sub-agents.
  • Between sessions, memory is storage you control: a fixed lookup for known facts, model-written notes for open-ended ones.
  • Retrieval puts only the relevant part of a big store into the context; its quality caps the answer's quality.
