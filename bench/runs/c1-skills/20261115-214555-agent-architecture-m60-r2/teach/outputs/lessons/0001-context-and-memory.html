Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context on each call, what gets saved between sessions, and how it finds the right page in a long manual.

The context window 9 min

Suppose a student asks your assistant about the laser cutter's settings for 3 mm acrylic. The model has never seen your makerspace's manual. How can it answer? Only if the manual's text is in what you send it. That text, plus everything else the model can use for a response, is the context window.

Anthropic's docs define the context window as "all the text a language model can reference when generating a response, including the response itself," and call it the model's working memory. They stress that it is different from the corpus the model was trained on (Claude docs: context windows).

For you as a programmer: the model is a stateless function. Each call is model(input_text) -> output_text. The context window is the maximum size of input + output. Nothing survives between calls unless your program puts it into the next input. The analogy stops at one place: a function's arguments have no size limit and no cost per byte, and the context does both.

What is inside it

The docs list what counts toward the window: the system prompt, every message in the conversation (tool results and documents included), the tool definitions, and the model's own output. Your tool descriptions from the agent-loop session are in there on every call.

Tokens: the unit of size and of cost

Windows are measured in tokens, not words. A token is a chunk of text the model reads and writes as one unit; a short common word is often one token, and a long or rare word, a part number or code is split into several. Window sizes are quoted in tokens: the docs list models with windows up to 1 million tokens, and older ones with 200,000.

Tokens also drive cost. Model providers bill by tokens read (input) and written (output), at different rates per token; check your provider's pricing page for the current numbers, because the rates change and this lesson uses only counts. What does not change is the shape of the bill: cost per request is roughly the tokens you send plus the tokens you receive, so anything you put in the context you pay for.

A common mix-up

"The model remembers what I told it earlier." This is tempting because chat apps feel like a continuing conversation. But the model keeps nothing between calls. The docs describe each turn as an input phase that holds all previous history plus the new message, and say the output becomes part of the next turn's input. The app is re-sending the history every time. If your program does not send it, the model does not have it.

What is kept between steps 10 min

Now put the window together with the agent loop. A student asks, "Is the laser cutter free tomorrow at 3 pm, and do I need training to use it?" If every step re-sends everything so far, how big does the input get by the last step?

Inside one request, the program keeps a growing list of messages. Each loop step appends two things: the model's tool request, and the tool's result. The next call sends the whole list. Between steps, then, the whole transcript is kept: nothing is dropped unless your program chooses to drop it.

Worked example: counting tokens for one request

Use made-up but plausible sizes. System prompt plus tool definitions: 1,500 tokens. Student question: 40. Each tool request from the model: 60. Calendar result: 200. Manual pages result: 3,000. Training record: 100. The final answer: 150.

  1. Call 1 input: 1,500 + 40 = 1,540. Output: tool request, 60.
  2. Call 2 input: call 1's input + the request (60) + the calendar result (200) = 1,800. Output: 60.
  3. Call 3 input: 1,800 + 60 + 3,000 = 4,860. Output: 60.
  4. Call 4 input: 4,860 + 60 + 100 = 5,020. Output: final answer, 150.
  5. Total input tokens billed: 1,540 + 1,800 + 4,860 + 5,020 = 13,220. Total output: 330.

The last call's input is 5,020 tokens, but you paid for 13,220 input tokens. The 3,000-token manual result was sent twice (in calls 3 and 4). The fixed 1,500 tokens of prompt and tools were sent four times. (Providers may discount repeated prefixes with prompt caching; the docs mention cached tokens still count toward the window.)

Two consequences for your design. First, tool results are usually the biggest items, so how much a tool returns matters more than how clever the prompt is. Anthropic's context-engineering article says tools should return token-efficient information (Effective context engineering for AI agents). Second, more steps cost more than linearly: each added step re-sends everything before it.

Check yourself

Bigger is not better: context rot 7 min

If windows hold up to a million tokens, why not paste the whole machine manual library into every request and be done? Cost is one reason: you saw above that you pay for every token on every call. The second reason is quality.

The docs say that as token count grows, accuracy and recall degrade, a phenomenon called context rot, which makes curating what is in context as important as how much space is available (Claude docs). Anthropic's engineering team describes it as a performance gradient rather than a hard cliff, and says models have an "attention budget" that every new token depletes. Their stated goal is the smallest possible set of high-signal tokens that gets the outcome you want (Anthropic Engineering).

A separate research result points the same way: in a study of multi-document question answering, models did best when the relevant passage was at the start or end of the input and worse when it was in the middle (Liu et al., "Lost in the Middle"). Treat that as evidence for the principle, not as a rule for current models: the paper tested models from 2023.

A common mix-up

"A bigger window means I do not need to choose what goes in." The window is a hard maximum, not a target. Past the maximum the request fails: the docs say the API returns an error if the input alone exceeds the window. Well before that, extra tokens cost money and can bury the passage that matters.

Keeping a long run small 7 min

Say a student spends 30 minutes asking about the laser cutter, and the transcript with tool results reaches the limit. The program has to decide what to throw away. There are three standard moves, and they are all things your program does, not the model.

  • Truncate: drop the oldest messages. Simple, but you lose what the student said first, which is often the goal of the whole conversation.
  • Clear old tool results: keep the record that a tool was called, but replace the bulky result with a short stub. Anthropic describes tool result clearing as one of the safest light-touch forms of trimming (Anthropic Engineering). Once the model has used the 3,000-token manual page, the page rarely needs to stay.
  • Compaction: when a conversation nears the limit, summarize it and start a new context window with the summary. Anthropic describes keeping decisions and unresolved problems and discarding redundant tool output. The risk is that a summary can drop a detail that turns out to matter later.
The docs name server-side compaction as their recommended primary strategy for long conversations, with context editing, such as clearing tool results, as an alternative. For a makerspace chat that rarely runs long, clearing tool results is likely enough; you can state that as a design decision.

What is kept between sessions: notes 11 min

A student finishes the laser cutter training on Monday and returns on Friday in a new chat. The new session starts with an empty context. How does the assistant know they are trained? Nothing in the model or the old window carries over. Whatever it knows on Friday must be written down somewhere on Monday and loaded on Friday.

That is the whole idea of memory between sessions: memory is storage outside the model that the program reads into the context when needed. Anthropic calls one form of it structured note-taking (also "agentic memory"): the agent regularly writes notes that are persisted outside the context window and pulls them back in later, as with a to-do list or a NOTES.md file (Anthropic Engineering). This workspace itself works that way: your tutor starts each session by reading NOTES.md.

One concrete mechanism: a memory tool

Anthropic's memory tool shows the pattern. It lets Claude "store and retrieve information across conversations in a directory of memory files." Claude works under a /memories directory and has commands to view, create, edit and delete files. Importantly, execution is client-side: "Claude only requests memory operations. Your application runs each request against storage you control and returns the result in a tool_result block" (Claude docs: memory tool).

You already know this shape: it is the agent loop from the earlier session. The memory tool is just another tool. The model asks to read a file, your program does it, the result goes into the next call. So memory the model reads is loaded into the context, and costs tokens like anything else. The docs describe this as just-in-time: the agent reads files on demand rather than loading everything up front.

Notes or a database?

Not all memory should be free-form notes. A design rule you can defend (this is judgment, not a quote from the docs):

Kind of factExampleWhere it fits
Must be exact and authoritativeStudent X passed laser cutter trainingA database that a tool queries, written by your program
Soft, helpful, can be wrongStudent prefers evening slotsA short note the model reads
Progress inside one long taskSteps done, steps leftA scratch note, discarded afterward

Training status gates access to dangerous equipment, so it should not rest on something the model wrote in a text file. The model could mis-write it, and the model's note could be stale.

A common mix-up

"Memory means the model learns from the conversation." It is tempting because the assistant seems to "know" the student next time. But no weights change; training and fine-tuning are out of scope for your project. The assistant knows only because text was saved and then put back into the context. If the note is not loaded, the knowledge is not there.

Security: the docs warn that a path like /memories/../../secrets.env could reach files outside the memory directory, so your handler must validate every path. They also say Claude usually refuses to write sensitive data but that you should add your own validation, and suggest capping file sizes and expiring old files. Student records are personal data, so decide what you store.

Retrieval: finding the right page 9 min

Your manuals are far too long to put in every request, as you saw. When a student asks about 3 mm acrylic settings, how does the assistant get just the right page into the context? That is retrieval: fetching the few pieces of stored text that are relevant to the current question and adding them to the context.

Anthropic's article contrasts two ways to do it (Anthropic Engineering):

  • Up front (pre-inference retrieval): before the model is called, your program searches the manuals using the student's question, often an embedding-based search, and puts the best passages in the first input. The model gets them without asking. It is fast and one model call, but if the search picked the wrong passages the model has nothing else to work with.
  • Just in time: the model gets a search tool or a page index, decides what to look up, reads the result, and can look again with a better query. The article notes the trade-off: runtime exploration is slower than retrieving up front. Claude Code is described as a hybrid: some files are loaded up front, others fetched on demand.

The article's advice for choosing is to do the simplest thing that works.

Making a long manual searchable

Whichever way, a long manual first has to be split into chunks: pieces small enough to return one or a few at a time, such as one section per chunk, with the machine name and section title attached. Search then ranks chunks against the question. Keyword search matches exact words (a part number, "kerf"); embedding search matches meaning (a question about "burn marks" finds a section titled "scorching"). Many systems use both. This lesson does not teach how embeddings are computed; for your design you need only know that a search tool returns the top few chunks.

Notice the link back to the budget. A search tool that returns the top 3 chunks of 400 tokens puts 1,200 tokens in the context, against the 3,000 or more you saw for a whole page, or the full library.

A common mix-up

"Retrieval means the model looks things up in the manuals itself." It does not read your files. Your program (or a tool you wrote) runs the search and returns text, and only that text enters the context. If the search returns the wrong chunk, the model answers from the wrong chunk, so tool and chunk quality decide the answer quality.

Worked example and practice 13 min

Worked example: a context plan for the booking path

Request: "Book me the 3D printer for Saturday afternoon." The assistant must check the student's training, check the calendar, book, and confirm. Plan what is in context and what is stored.

  1. Always in context (every call): a short system prompt with rules and the tool definitions, about 1,500 tokens. These are fixed costs, so keep the descriptions tight.
  2. Loaded at session start: this student's record from the database (name, trained machines), about 100 tokens. It is loaded once, by the program, because the student's identity is known before the model is called.
  3. Fetched by tools during the loop: calendar slots for Saturday only (not the whole month), as a compact list. The tool filters, the model does not.
  4. Not loaded: the 3D printer manual. The request does not ask about operating the machine, so no manual page is needed.
  5. Written afterward: the booking itself goes to the booking system by the book tool. A one-line note "prefers Saturday afternoons" may be added to the soft-notes store, with the student's consent.
  6. Trimming: the calendar result is cleared after the booking is confirmed if the chat continues.

Result: the context stays at a few thousand tokens, and each fact has one home.

Your turn

Request: "What power and speed do I use for 3 mm acrylic on the laser cutter, and am I allowed to use it yet?" Make the same plan. Step 1 is given: the system prompt and tool definitions are always in context. Decide steps 2 to 5 yourself: (2) what is loaded at session start, (3) what is fetched by tools and how you keep each result small, (4) what is not loaded, (5) what, if anything, is written for the next session.

Show a solution

2. The student's training record, loaded by the program at session start (or fetched with a tool if the identity is only known mid-chat).

3. A manual search tool that returns the top few chunks about acrylic settings for the laser cutter only, filtered by machine and capped in size; a training check tool if the record was not preloaded.

4. The other machines' manuals, the rest of the laser cutter manual, the calendar (not asked about).

5. Nothing is required. Do not write the settings into memory: the manual is the source of truth, and a stale copy in a note would be worse than looking it up again. At most, a note that this student works with acrylic, if it would help a later greeting and the student agrees.

If the training record says the student is not trained, the answer must say so before settings; that rule belongs in the system prompt.

Defending it at the design review 5 min

A reviewer asks: "Why not just give the model everything and let it sort it out?" You need answers that rest on reasons, not preference. Here are the decisions from this lesson as a table you can reuse, each with the reason a reviewer can test.

DecisionReasonWhat would change it
Search tool returns a few capped chunksEvery returned token is re-sent on each later call, and extra tokens can lower recallTests showing the model misses answers that sit just outside the top chunks
Training status in a database, queried by toolIt gates dangerous equipment, so it must be exact and written by your programNothing; this is a safety rule
Clear used tool results, no compaction at firstChats are short; clearing is simple and low-riskSessions that regularly reach the window limit
Soft preferences saved as short notes, with consentCheap to load, harmless if wrongA privacy rule from the makerspace or university
Fixed system prompt and tool list kept shortThey are re-sent on every call of every requestA need for more tools; then measure the cost

Notice the third column. A defensible design says what evidence would change it. You can measure the first and third rows on your own prototype: log the token counts per call, as in the worked example, and compare designs on real questions.

Summary 3 min

  • The model is stateless. Its context window, measured in tokens, is everything it sees on one call: prompt, tools, history, tool results and its own output.
  • Between steps, the program re-sends the growing transcript each call, so cost grows faster than the number of steps, and tool results are usually the biggest part.
  • More context is not better: it costs more and recall degrades (context rot). Trim with tool-result clearing, truncation or compaction.
  • Between sessions, nothing survives unless your program writes it to a store outside the model and loads it back. Exact facts belong in a database; soft notes can be files.
  • Retrieval puts only the relevant chunks of a long manual into the context, either up front or just in time through a search tool.
